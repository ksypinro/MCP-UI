# MCP / Agent-Tool Authentication & Authorization: Research Papers and Real-World Vulnerabilities/Incidents (through Oct 2026)

Labels used throughout: **[PR]** = peer-reviewed (journal/conference); **[PP]** = arXiv preprint, no confirmed venue; **[VB]** = vendor/security-research blog; **[ADV]** = CVE/GHSA/NVD advisory or vulnerability database; **[NEWS]** = press coverage; **[GUID]** = government / standards-body / industry-consortium guidance. "Attack class" tags follow the coordinator's vocabulary (confused deputy, token passthrough, token theft, SSRF via OAuth metadata, malicious authorization_endpoint, consent phishing/bypass, prompt injection → privileged tool call, tool poisoning/rug pull, cross-tenant leak, session hijacking, DNS rebinding of local servers, etc.).

## Q1. Which arXiv / conference papers analyse MCP security (emphasis on authN/authZ, consent, credentials)?

### Takeaway
The academic literature moved from 2025 threat taxonomies and attack benchmarks (Hou et al., MCPSecBench, MCPXKIT, "When MCP Servers Attack") to 2026 measurement studies that directly test OAuth deployments: the first remote-server auth study (Zhou et al., May 2026) found a flaw in every one of 119 testable OAuth-enabled MCP servers, dominated by Dynamic Client Registration (DCR) and PKCE weaknesses. Only a few MCP-security papers have confirmed peer-reviewed venues (ACM TOSEM, IEEE TDSC, DSN 2026, ICML 2025 position track, an IEEE ICNP workshop). I found no confirmed MCP paper at USENIX Security / NDSS / IEEE S&P 2026, and no academic paper on MCP Apps (UI extension) security.

### Cited Findings

#### A. Landscape / taxonomy papers
- **Hou, Zhao, Wang, Wang — "Model Context Protocol (MCP): Landscape, Security Threats, and Future Research Directions"** (Huazhong Univ. of Sci. & Tech.). arXiv 2503.23278, v1 30 Mar 2025, v3 7 Oct 2025 — [arXiv](https://arxiv.org/abs/2503.23278v3). **[PR]**: published in ACM TOSEM Vol. 35 Issue 10, Online AM 16 Feb 2026 — [ACM DL](https://dl.acm.org/doi/10.1145/3796519); also listed as FSE 2026 journal-first — [FSE 2026](https://conf.researchr.org/details/fse-2026/fse-2026-journal-first/37/Model-Context-Protocol-MCP-Landscape-Security-Threats-and-Future-Research-Direct).
  - Method: lifecycle analysis (v3: creation, deployment, operation, maintenance → 16 activities). Taxonomy: 4 attacker types (malicious developers, external attackers, malicious users, security flaws), 16 threat scenarios, real-world case studies, and per-phase safeguards. Data/code at GitHub security-pride/MCP_Landscape — [arXiv v3](https://arxiv.org/html/2503.23278v3).
  - Paper Digest ranked it the most influential 2025 arXiv cs.CR paper as of Sept 2025 — [Paper Digest](https://www.paperdigest.org/2025/09/most-influential-arxiv-cryptography-and-security-papers-2025-09-version/).
- **Song et al. — "Beyond the Protocol: Unveiling Attack Vectors in the MCP Ecosystem"** arXiv 2506.02040 (June 2025) — [arXiv](https://arxiv.org/pdf/2506.02040). Claims "first systematic study of attack vectors targeting the MCP ecosystem"; includes a malicious-external-resource vector (benign-looking server fetches attacker-poisoned web content that triggers chained invocation of other MCP servers). A Chinese write-up says it was accepted to IEEE TSE 2026 — [secrss](https://www.secrss.com/articles/91139) — **unverified with publisher, treat as [PP]**.
- **Namiot — "Security Analysis of the Model Context Protocol Specification"** arXiv 2601.17549 (Jan 2026) **[PP]**: argues MCP's weaknesses are architectural, not implementation-specific, requiring protocol-level remediation — [arXiv PDF](https://arxiv.org/pdf/2601.17549).
- **"A Systematic Security Analysis of Model Context Protocol: Vulnerabilities, Exploits, and Mitigations"**, 2026 IEEE 5th Int'l Conf. on AI in Cybersecurity (ICAIC), Houston, Feb 2026 **[PR, minor venue]**; reportedly finds 87% of examined MCP servers have at least one critical flaw — [IEEE Xplore](https://ieeexplore.ieee.org/document/11395848/) (figure from search snippet only; methodology not reviewed).
- **Yang, Bai, Lu — "Compatibility at a Cost: Systematic Discovery and Exploitation of MCP Clause-Compliance Vulnerabilities"** arXiv 2603.10163 (10 Mar 2026) **[PP]**: argues the MCP spec "relaxes many behavioral constraints into optional clauses," making SDKs prone to misuse ("compatibility-abusing attacks," e.g., silent prompt injection, DoS); builds a cross-language IR + static analysis + LLM reasoning pipeline over multi-language MCP SDKs — [arXiv](https://arxiv.org/abs/2603.10163). Abstract does not name auth clauses or CVEs.
- Additional 2026 preprints surfaced but **not reviewed** (titles only, for the report writer's awareness): MCP-DPT defense-placement taxonomy (arXiv 2604.07551), Attested Tool-Server Admission security extension (arXiv 2605.24248), CASCADE layered local defense (arXiv 2604.17125), MCP-in-SoS risk framework (arXiv 2603.10194), Threat modeling of MCP/A2A/Agora/ANP (arXiv 2602.11327), MCP threat modeling & tool poisoning (arXiv 2603.22489), A2ABreak (arXiv 2609.10871) — [search listing](https://arxiv.org/pdf/2604.07551); [2605.24248](https://arxiv.org/pdf/2605.24248); [2602.11327](https://arxiv.org/html/2602.11327v2); [2603.22489](https://arxiv.org/abs/2603.22489).

#### B. Attack studies and benchmarks
- **Radosevich & Halloran — "MCP Safety Audit: LLMs with the Model Context Protocol Allow Major Security Exploits"** arXiv 2504.03767 (v1 2 Apr 2025, v2 11 Apr 2025) **[PP]** — [arXiv](https://arxiv.org/abs/2504.03767). Shows leading LLMs can be coerced into using MCP tools to compromise a developer's system: malicious code execution (MCE), remote access control (RAC), **credential theft (CT)**; introduces a multi-server "RADE" attack; Claude and Llama-3.3-70B-Instruct vulnerable to all three; guardrail behavior varied by model and prompt wording; releases McpSafetyScanner — [arXiv PDF](https://arxiv.org/pdf/2504.03767).
- **Yang, Wu, Chen et al. — "MCPSecBench"** arXiv 2508.13220 (Aug 2025, revised) **[PP]**: taxonomy of 17 attack types across 4 surfaces (client, protocol, server, host); v2: >85% of attacks compromise at least one platform — [arXiv v2](https://arxiv.org/html/2508.13220v2); v3: core vulnerabilities affect Claude, OpenAI and Cursor, and existing protections achieve <30% average success — [arXiv v3](https://arxiv.org/html/2508.13220v3).
- **Guo et al. — "MCPXKIT: The Unified Toolkit for Analyzing MCP Security"** arXiv 2508.12538 (v1 18 Aug 2025; v2 25 May 2026) **[PR]**: accepted by IEEE Transactions on Dependable and Secure Computing (DOI 10.1109/TDSC.2026.3695553). 31 attack methods in 4 families (direct tool injection, indirect tool injection, malicious-user, LLM-inherent); agents over-trust tool descriptions, chained attacks exploit shared context — [arXiv](https://arxiv.org/abs/2508.12538). A 2026 paper cites an earlier "MCPLIB" by Guo et al. with the same 31-attack/4-family structure — [arXiv 2509.24272 search listing](https://arxiv.org/pdf/2509.24272); that MCPLIB = MCPXKIT is likely but not confirmed.
- **Zhao, Liu, Ruan, Li, Liang — "When MCP Servers Attack: Taxonomy, Feasibility, and Mitigation"** arXiv 2509.24272 (29 Sep 2025) **[PP]**: 12 attack categories with PoC malicious servers; attackers can mass-generate malicious servers "at virtually no cost"; state-of-the-art scanners insufficient — [arXiv](https://arxiv.org/abs/2509.24272).
- **Li & Gao (Univ. of Delaware) — "A First Look at the Security Issues in the MCP Ecosystem"** arXiv 2510.16558 **[PR: accepted to DSN 2026]** — [arXiv](https://arxiv.org/html/2510.16558). Auth/credential-relevant findings:
  - gitleaks over 5,659 mcp.so configs found 9 GitHub tokens, 5 still valid (July 2025); owners pasted their own PATs into config examples; attackers with write access could then inject malicious tool metadata. mcp.so did not respond — [arXiv](https://arxiv.org/html/2510.16558).
  - Registry hijacking: 212 of 1,379 invalid server links (15.37%) point to re-registrable GitHub accounts; 304 renamed accounts reclaimable; 408 npm "affix-squatting" groups (80.6% different maintainers) — [arXiv](https://arxiv.org/html/2510.16558).
  - Hosts (Cursor, Windsurf, Claude Desktop, Cline): none verified that LLM-returned tools still existed before invocation; Cursor invoked the first-listed tool on name collision; MCPInspect flagged 833 servers with exploitable code vulns (90.24% precision on a sample) — [arXiv](https://arxiv.org/html/2510.16558).
- **Majeed, Mahmoud, Nadi — "An Empirical Study of Model Context Protocol Applications"** arXiv 2607.25635 (28 Jul 2026) **[PP]**: 1,723 MCP *client* apps mined from GitHub; **only 37.2% gate tool execution behind a blocking approval step**; 85.2% configure servers via files; 81.1% use an official SDK. Note: "MCPApps" here = client apps, NOT the MCP Apps UI extension — [arXiv](https://arxiv.org/abs/2607.25635).

#### C. Measurement studies focused on authentication (detailed in Q3)
- **Zhou, Zhang, Zhang, Zhang, Zhang, Yang — "A First Measurement Study on Authentication Security in Real-World Remote MCP Servers"** arXiv 2605.22333 (21 May 2026) **[PP]** — [arXiv abs](https://arxiv.org/abs/2605.22333). Taxonomy of 4 categories / 9 flaws — [arXiv HTML](https://arxiv.org/html/2605.22333v1):
  - C1 DCR flaws: F1 *Malicious DCR Binding* (DCR endpoint accepts arbitrary `redirect_uri` from anonymous requesters); F2 *Blind Client Trust* (unregistered `client_id` accepted).
  - C2 Delegated-authorization flaws: F3 *Layer Inconsistency* (PKCE enforced on MCP layer but not upstream); F4 *Nested Context Pollution* (downstream `redirect_uri` embedded in upstream `state` without integrity/allowlist).
  - C3 Open-client-environment flaws: F5 *PKCE Downgrade* (no `code_challenge` or `plain` accepted); F6 *Consent Page Bypass* (consent page omits `redirect_uri`, enabling localhost impersonation).
  - C4 Common OAuth misconfigs: F7 Open Redirect; F8 Weak State (CSRF); F9 Code Replay.
  - Threat model explicitly includes "confused deputy attacks against upstream resources" arising from the MCP server's dual AS/client role; token passthrough/audience are discussed only as spec background (RFC 8707, 2025-06-18 spec) — [arXiv HTML](https://arxiv.org/html/2605.22333v1).
- **Padilla (CobaltoSec) — "Exposed by Design: A Dynamic Security Assessment of Internet-Facing MCP Servers at Scale"** arXiv 2608.00150 (31 Jul 2026) **[PP, single author]** — [arXiv](https://arxiv.org/html/2608.00150).
- **Sohail — "Characterizing Network Centralization and Observability in the Remote MCP Ecosystem"** arXiv 2609.19100 (16 Sep 2026) **[PR: IEEE ICNP NIPA 2026 workshop]** — [arXiv](https://arxiv.org/abs/2609.19100).
- **Li et al. (Shandong Univ.) — "We Urgently Need Privilege Management in MCP: A Measurement of API Usage in MCP Ecosystems"** arXiv 2507.06250 (July 2025) **[PP]** — static analysis of 2,562 MCP apps / 23 categories; network APIs in 1,438 servers and system-resource APIs in 1,237; less popular plugins disproportionately contain high-risk operations; case studies of privilege escalation, misinformation, data tampering; calls for dynamic permission models — [arXiv](https://arxiv.org/html/2507.06250v1).
- **Hasan et al. (Queen's Univ.) — "MCP at First Glance: Studying the Security and Maintainability of MCP Servers"** arXiv 2506.13538 **[PP]** — 1,899 open-source servers; 8 distinct vulnerability types (only 3 overlap traditional software vulns); 7.2% contain general security issues — [arXiv v3](https://arxiv.org/html/2506.13538v3).

#### D. Defense / mitigation papers
- **Narajala & Habler — "Enterprise-Grade Security for the MCP: Frameworks and Mitigation Strategies"** arXiv 2504.08623 (11 Apr 2025; v2 2 May 2025) **[PP]**: defense-in-depth, Zero Trust, rigorous tool vetting, continuous monitoring, I/O validation — [arXiv](https://arxiv.org/abs/2504.08623v1); AWS / Intuit A2RS collaboration per [alphaXiv](https://alphaxiv.org/overview/2504.08623v2).
- **Kumar, Girdhar, Patil, Tripathi — "MCP Guardian: A Security-First Layer for Safeguarding MCP-Based AI System"** arXiv 2504.12757 (2025) **[PP]**: middleware overriding `invoke_tool`; API-token authentication per request with optional per-token tool restriction (read-only vs admin); per-token rate limiting (example 5 req/min); WAF scanning; logging — [arXiv PDF](https://arxiv.org/pdf/2504.12757). Claimed 10–15% latency overhead is from a third-party summary only — [alphaXiv](https://alphaxiv.org/overview/2504.12757v2).
- **Bhatt, Narajala, Habler — "ETDI: Mitigating Tool Squatting and Rug Pull Attacks in MCP by using OAuth-Enhanced Tool Definitions and Policy-Based Access Control"** arXiv 2506.01333 (2 Jun 2025) **[PP]**: cryptographic tool identity (vs squatting), immutable versioned tool definitions (vs rug pull), explicit OAuth-scoped permissions, runtime policy engine beyond static scopes — [arXiv](https://arxiv.org/abs/2506.01333). Distinguishes tool-identity verification from the tool acting as OAuth Resource Server that declares required issuer/scopes — [arXiv PDF](https://arxiv.org/pdf/2506.01333). Reference implementation PR to the Python SDK — [GitHub PR #845](https://github.com/modelcontextprotocol/python-sdk/pull/845). Cited as IEEE CARS 2025 by a 2026 paper — [arXiv 2605.22333](https://arxiv.org/pdf/2605.22333) (venue unverified).
- **Debenedetti et al. (Google/ETH) — "Defeating Prompt Injections by Design" (CaMeL)** arXiv 2503.18813 (v1 24 Mar 2025, v2 24 Jun 2025) **[PP]**: separates control flow (from trusted query) from data flow so untrusted data cannot alter program flow; capability metadata on values enforces policies at tool-call time to block exfiltration; 77% of AgentDojo tasks solved with provable security vs 84% undefended — [arXiv](https://arxiv.org/abs/2503.18813).
- **Debenedetti et al. — "AgentDojo"** arXiv 2406.13352 (June 2024): 97 tasks, 629 security test cases for prompt-injection against tool-using agents — [arXiv](https://arxiv.org/abs/2406.13352); unveiled at NeurIPS 2024 — [Invariant Labs](https://invariantlabs.ai/blog/agentdojo) (Datasets & Benchmarks track not confirmed from sources retrieved).
- **Shi, He, Wang, Li, Wu, Guo, Song — "Progent: Programmable Privilege Control for LLM Agents"** arXiv 2504.11703 (Apr 2025, v2 Aug 2025) **[PP]**: least privilege at tool-call level via a DSL policy, deterministic enforcement; AgentDojo ASR 41.2% → 2.2%; ASB 70.3% → 7.3% (0% with manual policies) — [arXiv](https://arxiv.org/html/2504.11703v2).

#### E. Agent identity / delegated authorization
- **South, Marro, Hardjono, Mahari, Whitney, Chan, Pentland — "Authenticated Delegation and Authorized AI Agents"** arXiv 2501.09674 (Jan 2025) — [arXiv](https://arxiv.org/html/2501.09674v1); **[PR]** published as "Position: AI Agents Need Authenticated Delegation," ICML 2025 (oral) — [ICML](https://icml.cc/virtual/2025/oral/40173); [MLAnthology](https://mlanthology.org/icml/2025/south2025icml-position). Proposes extending OAuth 2.0/OIDC with agent-specific credentials: user ID token, agent ID token, and a delegation token scoping the agent's authority; translating natural-language permissions into auditable access-control configs; tokens embeddable in W3C Verifiable Credentials — [arXiv](https://arxiv.org/html/2501.09674v1).
- **OpenID Foundation — "Identity Management for Agentic AI"** (7 Oct 2025; lead author Tobin South; arXiv 2510.25819) **[GUID]**: OAuth 2.1/OIDC adequate for single-domain agents but gaps for cross-domain, async, highly autonomous agents: agent identity fragmentation, user impersonation, **consent fatigue**, recursive delegation, and browser/computer-use agents bypassing API authorization controls — [OpenID Foundation](https://openid.net/new-whitepaper-tackles-ai-agent-identity-challenges/); [arXiv](https://arxiv.org/abs/2510.25819).
- **Goswami — "Agentic JWT" IETF individual draft** (draft-goswami-agentic-jwt-00, Dec 2025; -01 June 2026) **[GUID, non-WG draft]**: agent identity from checksum of system prompt/tools/config, workflow-bound tokens, new `agent_checksum` grant type, proof-of-possession against inter-agent token replay — [IETF](https://datatracker.ietf.org/doc/html/draft-goswami-agentic-jwt-00).

#### G. MCP Apps (UI extension) security — academic coverage
- No arXiv/conference paper on MCP Apps (SEP-1865, `ui://` resources in sandboxed iframes) security was found. SEP-1865 itself lists mandatory iframe sandboxing with auditable communication as a core element and chose HTML-only for the simplest security model — [MCP SEP-1865](https://modelcontextprotocol.io/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp). The only MCP-Apps-specific disclosure found is a low-severity postMessage origin bug (CVE-2026-76894, see Q2).

### Inferences
- Academic emphasis has shifted: 2025 work treats auth mostly as one category among many (credential theft in MCP Safety Audit; "improper authentication" in taxonomies), whereas 2026 measurement work (Zhou et al.) is the first to systematically test OAuth flows and finds that MCP-specific features (DCR, open public clients, MCP-server-as-OAuth-proxy) create new flaw classes beyond classic OAuth misconfigs.
- Defensive research converges on *system-level* enforcement (capabilities/CaMeL, privilege policies/Progent, signed+versioned tool definitions/ETDI, middleware auth/MCP Guardian) rather than model alignment — consistent with the incident record in Q2 where the root cause is over-privileged credentials reachable from untrusted content.
- Peer-reviewed coverage is thin relative to preprints; the report should weight TOSEM/TDSC/DSN/ICML items more heavily and present 2026 measurement preprints as indicative.

### Gaps
- Could not confirm any MCP-specific paper in USENIX Security 2026, NDSS 2026, IEEE S&P 2026, or CCS 2025 (accepted-paper lists not retrieved).
- "Beyond the Protocol" TSE acceptance and ETDI IEEE CARS venue unverified; AgentDojo's NeurIPS track unverified from retrieved sources; CaMeL has no venue listed on arXiv.
- No academic study of MCP Apps / UI-extension security (iframe sandbox, postMessage, CSP, UI-driven tool calls) found through Oct 2026.
- Full texts of NSA CSI (HTTP 403) and CoSAI paper not retrieved; their specific auth recommendations are from secondary summaries.

## Q2. Which real vulnerabilities and incidents involve MCP (and agent-tool) authentication/authorization?

### Takeaway
Disclosed issues cluster into (1) **malicious-server-controlled OAuth metadata** abused by clients (mcp-remote CVE-2025-6514 RCE; MCP Python SDK OAuth credential theft, Sept 2026; mcp-remote device-code cleartext, Oct 2026); (2) **MCP-server-as-OAuth-proxy flaws** — confused deputy via static client_id + consent cookie, unbound `state`, DCR with arbitrary redirect URIs (Obsidian/Square, Obot, Cloudflare workers-oauth-provider, the 9 CVEs from Zhou et al.); (3) **unauthenticated or fail-open local/remote endpoints** (MCP Inspector CVE-2025-49596, SDK DNS-rebinding defaults CVE-2025-66414/66416, LiteLLM CVE-2026-59822 in CISA KEV, OpenClaw token leak); (4) **over-privileged credentials + prompt injection** (GitHub MCP, Supabase service_role, ChatGPT Connectors AgentFlayer, Claude Desktop extensions); (5) **authorization logic / tenant isolation bugs** (Asana cross-tenant, Filesystem/Git/Postgres reference-server sandbox & read-only bypasses); and (6) **credential exposure in supply chain/hosting** (Smithery Fly.io token, postmark-mcp BCC, Claude Code API-key leak, Moltbook).

### Cited Findings

Items are chronological by disclosure. Each lists date, source type, what went wrong, auth root cause, fix, attack class.

#### 2025

1. **Equixly audit of popular MCP servers** (29 Mar 2025) **[VB]** — command injection in 43% of tested implementations, SSRF 30%, path traversal/arbitrary file read 22%; of notified developers 30% fixed, 45% called risks theoretical/acceptable, 25% never replied — [Equixly](https://equixly.com/blog/2025/03/29/mcp-server-new-security-nightmare). Sample size not stated. *Attack class: server-side injection reachable by agent; SSRF.*

2. **Cloudflare `workers-oauth-provider` (MCP auth library) — CVE-2025-4143 & CVE-2025-4144** (~1 May 2025) **[ADV]**
   - CVE-2025-4143: `redirect_uri` checked only at token exchange, not at authorization; victim who previously authorized a client could be phished to leak credentials where the app auto-approves previously-authorized clients — [NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-4143); [Kodem](https://www.kodemsecurity.com/cve-archive/cve-2025-4143).
   - CVE-2025-4144: PKCE check could be skipped ("completely bypasses PKCE protection"). Both fixed in 0.0.5 (PRs #26, #27) — [Kodem](https://www.kodemsecurity.com/cve-archive/cve-2025-4143). CVSS conflicts across databases (4144: 9.8 vs 5.3) — [Shodan CVEDB](https://cvedb.shodan.io/dashboard/cve/CVE-2025-4143).
   - *Attack class: authorization-code theft via open redirect; PKCE bypass.*

3. **Trail of Bits — "Insecure credential storage plagues MCP"** (30 Apr 2025) **[VB]** — official and third-party servers (GitLab, Postgres, Google Maps, Figma connector, Superargs) store long-lived third-party API keys in plaintext config files, sometimes world-readable; exposed to local malware, unrelated file-read bugs, shared hosts, backup sync — [Trail of Bits](https://blog.trailofbits.com/2025/04/30/insecure-credential-storage-plagues-mcp/). *Attack class: credential theft at rest.*

4. **GitHub MCP server "toxic agent flow" (Invariant Labs)** (26 May 2025) **[VB]** — attacker files a prompt-injection issue on a public repo; user asks agent (Claude 4 Opus in Claude Desktop) to review issues; agent reads private repos via the user's GitHub credentials and leaks contents (incl. salary and relocation data in demo) into a PR on the public repo. Invariant calls it "a fundamental architectural issue," not a GitHub server code bug; users often click "Always Allow." Mitigations: least-privilege/granular tokens, a "one repo per session" guardrail policy, runtime monitoring (MCP-scan proxy) — [Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability); toxic-flow analysis follow-up — [Invariant](https://invariantlabs.ai/blog/toxic-flow-analysis). *Attack class: prompt injection → privileged tool call; over-scoped credential (confused-deputy-like).*

5. **MCP Inspector — CVE-2025-49596 (CVSS 9.4)** (CVE/GHSA published 13 Jun 2025; Oligo write-up 27 Jun 2025) **[VB+ADV]** — Inspector's Node proxy had **no authentication between web client and proxy** and would spawn stdio commands; reachable from public web pages via CSRF, the browser "0.0.0.0-day," and DNS rebinding. Anthropic had a prior report on 26 Mar 2025; Oligo reported 18 Apr 2025. Fix in 0.14.1: session token required by default (Jupyter-style), allowed-origin verification, Host/Origin header checks — [Oligo](https://www.oligo.security/blog/critical-rce-vulnerability-in-anthropic-mcp-inspector-cve-2025-49596); [Recorded Future](https://www.recordedfuture.com/blog/anthropic-mcp-inspector-cve-2025-49596). *Attack class: unauthenticated local proxy; DNS rebinding/CSRF → RCE.*

6. **Smithery.ai hosting — path traversal → Fly.io token (GitGuardian)** (reported 13 Jun 2025, fixed ~15 Jun 2025; one source dates disclosure Oct 2025) **[VB/NEWS]** — unvalidated `dockerBuildPath` in `smithery.yaml` let a malicious build read `~/.docker/config.json` containing an **over-privileged Fly.io token** that controlled Smithery's machines API, covering >3,000 apps (mostly hosted MCP servers); attacker could intercept traffic carrying clients' API keys. Token rotated, flaw fixed; no evidence of exploitation — [SC World](https://www.scworld.com/news/smithery-ai-fixes-path-traversal-flaw-that-exposed-3000-mcp-servers); [iTWire](https://itwire.com/business-it-news/security/from-path-traversal-to-supply-chain-compromise-breaking-mcp-server-hosting.html). *Attack class: hosting-platform credential exposure; supply chain.*

7. **Asana MCP server cross-tenant data exposure** (feature launched 1 May 2025; bug found 4 Jun; MCP offline 5–17 Jun; customers told 16 Jun; public 18 Jun 2025) **[NEWS]** — a "logic flaw," not a hack, let MCP users see data (tasks, project metadata, team info, comments, files) from other organizations within the scope of their own permissions; ~1,000 customers potentially affected; no evidence data was actually viewed — [BleepingComputer](https://bleepingcomputer.com/news/security/asana-warns-mcp-ai-feature-exposed-customer-data-to-other-orgs/); [The Register](https://theregister.com/2025/06/18/asana_mcp_server_bug/) (notes Asana gave no coding-error details). Root cause characterized by third parties as a flawed tenant-isolation check / cached responses without re-verifying tenant context — [UpGuard](https://upguard.com/blog/asana-discloses-data-exposure-bug-in-mcp-server); [PolicyLayer](https://policylayer.com/attacks/confused-deputy) (secondary, unconfirmed by Asana). Fix: code fix; MCP connections reset forcing re-authorization. Exposure window disputed (from 1 May vs June only). *Attack class: cross-tenant leak / broken object-level authorization.*

8. **Backslash "NeighborJack"** (25 Jun 2025) **[VB]** — of ~15,000 servers analyzed, hundreds explicitly bound to 0.0.0.0, reachable by anyone on the same LAN (café/co-working scenario), some combined with OS command injection and excessive permissions → host takeover; none found malicious — [Backslash](https://www.backslash.security/blog/hundreds-of-mcp-servers-vulnerable-to-abuse); [Virtualization Review](https://virtualizationreview.com/Articles/2025/06/25/MCP-Servers-Hit-by-NeighborJack-Vulnerability-and-More.aspx). *Attack class: unauthenticated network exposure of local servers.*

### Inferences
- **Client-side trust in server-supplied OAuth metadata is a recurring root cause** (6514 authorization_endpoint → shell; Python SDK issuer/fallback → credential theft; device-code endpoints over HTTP). The spec's 2025-11-25 SSRF and authorization-URL-validation sections address some but not all (issuer binding and credential-to-AS binding were SDK bugs as late as Sept 2026).
- **The MCP-server-as-OAuth-proxy pattern is the dominant server-side auth failure** (Obsidian, Obot, Cloudflare lib, Zhou et al.'s 96.6% DCR flaw rate), driven by DCR with unrestricted redirect URIs, static upstream client IDs, and weak consent/state handling.
- **Most "data exfiltration" incidents are authorization-scope problems, not authentication failures:** the credentials were valid but over-broad (GitHub PAT, Supabase service_role, connector OAuth grants, Fly.io token), and prompt injection supplied the intent.
- **Fail-open and insecure defaults** (LiteLLM fallback, SDK DNS-rebinding defaults, Inspector without session token, 0.0.0.0 binding) recur; vendors fixed them by flipping defaults.
- The pace accelerated in 2026 (KEV-listed MCP gateway bug, official SDK OAuth bug, Azure MCP managed-identity leak), indicating MCP auth bugs now affect production enterprise infrastructure, not just developer tools.

## Q3. What do measurement studies say about how many public MCP servers lack authentication or mishandle tokens?

### Takeaway
Every large-scale measurement shows a large unauthenticated share, though numbers vary by population: ~40.55% of 7,973 live remote servers expose tools with no auth (Zhou et al., May 2026); 91.8% of 414 audited internet-facing servers lack OAuth (Padilla, Jul 2026); 119/119 verified servers answered `tools/list` unauthenticated (Knostic, Jul 2025); 492 servers had neither auth nor TLS (Trend Micro, Jul 2025). Where auth exists it is mostly static secrets (Astrix: 53% static vs 8.5% OAuth across 5,200 open-source servers), and OAuth implementations are frequently flawed (100% of 119 testable OAuth servers had ≥1 flaw). Platform-hosted servers fare much better (95% of PaaS-hosted servers enforce OAuth 2.1+PKCE).

### Cited Findings

#### Internet scans of remote/exposed servers
- **Zhou et al. (arXiv 2605.22333, May 2026) [PP]:** FOFA/Shodan → 28,715 candidates → 7,973 live servers validated by MCP `initialize` handshake (1% false positive in 100-sample review). Auth status: **no auth 3,233 (40.55%)**, OAuth 2,428 (30.45%), static token/API key 2,312 (29.00%). Of OAuth servers, 1,118 (46.0%) advertise a `registration_endpoint` (DCR) — [arXiv HTML](https://arxiv.org/html/2605.22333v1).
  - Of 119 fully testable OAuth servers: **all had ≥1 flaw, 325 flaws total**; DCR flaws in 115 (96.6%) — Malicious DCR Binding 114 (95.8%), Blind Client Trust 12 (10.1%); open-client flaws 102 (85.7%) — PKCE downgrade 81 (68.1%), consent page bypass 72 (60.5%); delegated-auth flaws 18 (15.1%); common OAuth misconfigs 34 (28.6%) — open redirect 28 (23.5%), code replay 6 (5.0%), weak state 3 (2.5%); 39 (32.8%) flagged in ≥3 categories; 81/119 (68.1%) use delegated authorization, of which 40 (49.4%) use nested `state` — [arXiv HTML](https://arxiv.org/html/2605.22333v1). Detector precision 85.75%, recall 99.69% — [arXiv HTML](https://arxiv.org/html/2605.22333v1). (Paper has minor internal inconsistencies, e.g., PKCE downgrade 68.1% vs 67.5%.)
- **Padilla, "Exposed by Design" (arXiv 2608.00150, Jul 2026) [PP]:** passive discovery from 11 sources + handshake; 4 runs 15–24 Jul 2026; 640 confirmed servers, 414 dynamically audited; **91.8% (380/414) lacked OAuth**; many static bearer tokens "predictable or empty"; in one run 106 servers exposed tools invocable with no credential; 687 tool instances expose shell execution without access control; token exposure (MCP07) on 18 servers; SSRF CRITICAL on 29; command injection CRITICAL on 38; 41.6% of confirmed servers disappear within three days; cites Censys estimate of >21,000 MCP endpoints — [arXiv](https://arxiv.org/html/2608.00150).

- **Trend Micro (July 2025) [VB]:** **492 MCP servers with no client authentication or traffic encryption**, exposing 1,402 tools, >90% offering direct read access to the data source; ~74% hosted on AWS/Azure/GCP; root causes: hardcoded data-source credentials in server config, binding to 0.0.0.0, all clients sharing the same privileged access — [Trend Micro](https://www.trendmicro.com/vinfo/hk/security/news/cybercrime-and-digital-threats/mcp-security-network-exposed-servers-are-backdoors-to-your-private-data); follow-up urging treatment as cloud infrastructure — [Trend Micro update](https://www.trendmicro.com/vinfo/kr/security/news/vulnerabilities-and-exploits/update-on-exposed-mcp-servers-the-threat-widens-to-the-cloud).
- **Backslash (25 Jun 2025) [VB]:** ~15,000 servers analyzed; hundreds bound to 0.0.0.0 (LAN-reachable) — [Backslash](https://www.backslash.security/blog/hundreds-of-mcp-servers-vulnerable-to-abuse).
- **Sohail (arXiv 2609.19100, Sep 2026) [PR-workshop]:** 179 remote endpoints from two registries; **95% of commercial PaaS-hosted servers enforce gateway-level OAuth 2.1 with PKCE**; authentication driven by hosting-platform choice rather than operator configuration; strong ASN concentration (HHI 0.736); platform auth limits independent scanning ("Security-Observability Tradeoff") — [arXiv](https://arxiv.org/abs/2609.19100). (A search snippet claimed "zero Smithery servers permit unauthenticated access vs 35% of external servers" but the fetched abstract did not name Smithery — unverified.)

#### Code/config studies of open-source servers (credential handling)
- **Astrix "State of MCP Server Security 2025" (15 Oct 2025) [VB]:** >5,200 open-source servers; **88% require credentials; 53% rely on long-lived static secrets (API keys, PATs); only 8.5% use OAuth; 79% of API keys passed via plain environment variables** — [Astrix](https://astrix.security/learn/blog/state-of-mcp-server-security-2025/).
- **Trail of Bits (30 Apr 2025) [VB]:** plaintext, sometimes world-readable credential files across official and third-party servers — [Trail of Bits](https://blog.trailofbits.com/2025/04/30/insecure-credential-storage-plagues-mcp/).
- **Li & Gao (DSN 2026) [PR]:** 9 GitHub tokens leaked in 5,659 mcp.so configs, 5 valid — [arXiv](https://arxiv.org/html/2510.16558).
- **Li et al. (arXiv 2507.06250) [PP]:** 2,562 MCP apps; network APIs in 1,438 and system-resource APIs in 1,237 servers with minimal isolation — [arXiv](https://arxiv.org/html/2507.06250v1).
- **Majeed et al. (arXiv 2607.25635) [PP]:** only 37.2% of 1,723 MCP client apps gate tool execution behind blocking approval — [arXiv](https://arxiv.org/abs/2607.25635).
- **Obsidian (Jan 2026) [VB]:** CIMD (Client ID Metadata Documents) adopted by only 3 of 78 servers tested — [Obsidian](https://www.obsidiansecurity.com/blog/when-mcp-meets-oauth-common-pitfalls-leading-to-one-click-account-takeover).
- Secondary/unverified figures circulating: "only 18% of deployments implement access scoping" (NHI Mgmt Group, original source unknown) — [NHIMG](https://nhimg.org/articles/internet-exposed-mcp-servers-are-broadcasting-tools-without-auth/); "Feb 2026 audit of official MCP Registry found 41% (214) with zero auth" (third-party blog) — [mcpplaygroundonline](https://mcpplaygroundonline.com/blog/mcp-server-security-complete-guide-2026). Treat both as unverified.

### Inferences
- Across 2025–2026 studies the unauthenticated share among *internet-reachable* servers ranges roughly 40%–100% depending on sampling (Shodan-fingerprinted self-hosted endpoints skew worst; registry/PaaS-hosted skew best). The trend is toward OAuth for hosted servers, but self-hosted endpoints remain largely open.
- OAuth adoption alone does not equal secure auth: DCR without redirect restrictions and missing PKCE enforcement were near-universal in the one study that tested flows.
- Static secrets in env vars / config files remain the norm for local (stdio) servers, so credential theft from the developer host (malicious server, file-read bug, prompt-injected command execution) remains a primary path.
- Results are not directly comparable (different populations, methods, timeframes); the report should present ranges with population context.

### Gaps
- No longitudinal study tracking the same population's auth posture over time was found (Padilla notes high churn: 41.6% disappear in 3 days).
- No measurement of token audience validation / token-passthrough prevalence in deployed servers was found (Zhou et al. did not include it as a tested flaw).
- No measurement of MCP Apps (UI resource) security posture found.

## Q4. What lessons do papers/incidents draw about where credentials should live, consent, and least privilege?

### Takeaway
The convergent lessons are: (1) keep credentials out of the model's reach and out of plaintext configs, scope them minimally, bind them to their intended audience/authorization server, and never pass client tokens through; (2) consent must be bound to *what* is approved (client identity, redirect URI, exact command/config hash) and must precede any credential-bearing action; and (3) least privilege must be enforced deterministically at the system/tool-call layer, because prompt injection makes the model an untrustworthy decision-maker.

### Cited Findings

#### Where credentials should live / how they should be bound
- MCP servers **MUST NOT accept tokens not explicitly issued for the MCP server** (token passthrough forbidden); passthrough breaks rate limiting/audit, lets a stolen token use the server as an exfiltration proxy, and enables cross-service reuse — [MCP Security Best Practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices).
- Audience validation and restricting tokens to the specific MCP were the fix for Obot's DCR takeover — [VulnCheck](https://www.vulncheck.com/advisories/obot-before-0.23.0-authentication-bypass-via-oauth-dynamic-client-registration).
- OAuth clients must validate AS `issuer` and bind stored client credentials to the AS they were issued by; treat an untrusted MCP server as an authentication boundary, not just a tool endpoint — [Mend.io (Python SDK flaw)](https://www.mend.io/vulnerability-database/WS-2026-0089/); [CSA research note](https://labs.cloudsecurityalliance.org/wp-content/uploads/2026/09/CSA_research_note_mcp_python_sdk_oauth_flaw_20260930-csa-styled.pdf).
- Clients should require HTTPS for OAuth URLs (http only for loopback), block private/link-local ranges, validate redirect hops, use egress proxies, and pin DNS between check and use to avoid SSRF via OAuth metadata — [MCP Security Best Practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices).
- Avoid plaintext credential files; load from secret managers / OS vaults at runtime — [Trail of Bits](https://blog.trailofbits.com/2025/04/30/insecure-credential-storage-plagues-mcp/); vault-referenced config example — [Trend Micro](https://trendmicro.com/vinfo/us/security/news/vulnerabilities-and-exploits/beware-of-mcp-hardcoded-credentials-a-perfect-target-for-threat-actors). Astrix recommends OAuth delegation over static PATs/API keys — [Astrix](https://astrix.security/learn/blog/state-of-mcp-server-security-2025/).
- Don't give agents super-user database credentials: `service_role` bypasses RLS; use read-only, project-scoped, feature-limited configs — [General Analysis](https://generalanalysis.com/blog/supabase-mcp-blog); read-only transactions are insufficient against multi-statement input, so enforce at DB role level — [Datadog](https://securitylabs.datadoghq.com/articles/mcp-vulnerability-case-study-SQL-injection-in-the-postgresql-mcp-server/).
- Build/hosting infrastructure credentials must be narrowly scoped; one over-privileged Fly.io token exposed >3,000 hosted servers — [SC World](https://www.scworld.com/news/smithery-ai-fixes-path-traversal-flaw-that-exposed-3000-mcp-servers).
- Centralized custody of agent OAuth/refresh tokens is a high-value target (Drift tokens used against Salesforce; GTIG advised treating connected data as compromised and rotating secrets found in it) — [Security Affairs](https://securityaffairs.com/181632/hacking/unc6395-targets-salesloft-in-drift-oauth-token-theft-campaign.html).
- Delegation should be explicit and auditable: user ID token + agent ID token + scoped delegation token — [South et al., ICML 2025](https://arxiv.org/html/2501.09674v1); explicit on-behalf-of delegation and interoperable agent identity profiles — [OpenID Foundation](https://openid.net/new-whitepaper-tackles-ai-agent-identity-challenges/); token exchange (RFC 8693) with `act` claim preserves original subject — [Red Hat](https://next.redhat.com/2026/02/26/zero-trust-for-autonomous-agentic-ai-systems-building-more-secure-foundations/).

#### Consent
- MCP proxy servers MUST obtain **per-client consent** before forwarding to third-party AS; consent UI MUST name the client, show scopes and the registered `redirect_uri`, use CSRF protection and anti-framing; consent cookies MUST use `__Host-`, Secure/HttpOnly/SameSite=Lax, be signed and bound to `client_id`; `state` MUST be random, stored only after consent, single-use, short-lived — [MCP Security Best Practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices).
- Always display the exact `redirect_uri` and warn on localhost callbacks; restrict DCR redirect patterns, rate-limit/attest DCR, migrate to CIMD; enforce PKCE S256 server-side; keep upstream routing context server-side behind an opaque `state`; elevate PKCE/DCR restrictions to MUST in the spec — [Zhou et al.](https://arxiv.org/html/2605.22333v1).
- Consent must bind to content, not names: MCPoison exploited approval keyed on config name — [Check Point](https://research.checkpoint.com/2025/cursor-vulnerability-mcpoison/); ETDI proposes signed, immutable, versioned tool definitions so changes require re-approval — [ETDI](https://arxiv.org/abs/2506.01333).
- Consent must precede credential use: Claude Code sent the API key before the trust prompt — [Check Point Research](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/).
- One-click local server install MUST show the full command and require explicit approval; servers should run sandboxed with minimal default privileges — [MCP Security Best Practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices).
- Consent fatigue undermines approval: users choose "Always Allow" — [Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability); OIDF names consent fatigue as a key gap — [OpenID Foundation](https://openid.net/new-whitepaper-tackles-ai-agent-identity-challenges/); only 37.2% of MCP client apps gate tool calls behind approval — [Majeed et al.](https://arxiv.org/abs/2607.25635). Server-initiated sampling can trigger tool calls without user awareness — [Unit 42](https://unit42.paloaltonetworks.com/model-context-protocol-attack-vectors/).

#### Least privilege and system-level enforcement
- Progressive scope model: minimal initial scopes, step-up via `WWW-Authenticate scope=` challenges, avoid publishing all scopes in `scopes_supported` or wildcard scopes — [MCP Security Best Practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices).
- Granular repo-scoped tokens and "one repo per session" policies to block cross-repo exfiltration — [Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability).
- Deterministic tool-call privilege policies (Progent) cut attack success to ~2% on AgentDojo — [Progent](https://arxiv.org/html/2504.11703v2); capability-tagged data flows (CaMeL) block unauthorized exfiltration with provable guarantees — [CaMeL](https://arxiv.org/abs/2503.18813).
- MCP plugins inherit broad system privileges with little isolation; need dynamic permission models and automated trust assessment — [Li et al.](https://arxiv.org/html/2507.06250v1).
- Run servers with minimum privileges to contain path/sandbox escapes — [Cymulate](https://cymulate.com/blog/cve-2025-53109-53110-escaperoute-anthropic/); Claude Desktop extensions ran unsandboxed with full user privileges — [Koi](https://www.koi.ai/blog/promptjacking-the-critical-rce-in-claude-desktop-that-turn-questions-into-exploits).
- Authenticate by default: SDKs should default HTTP transport to OAuth 2.1 and require explicit opt-out; registries should display auth posture; hosts should warn on unauthenticated shell-capable deployments — [Padilla](https://arxiv.org/html/2608.00150). Local servers should use stdio or require a token / IPC with restricted access; DNS-rebinding protection on by default — [MCP Security Best Practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices); [OSV GHSA-9h52-p55h-vw2f](https://osv.dev/vulnerability/GHSA-9h52-p55h-vw2f). Never expose servers without an auth/proxy layer; limit server permissions — [Trend Micro](https://www.trendmicro.com/vinfo/hk/security/news/cybercrime-and-digital-threats/mcp-security-network-exposed-servers-are-backdoors-to-your-private-data).
- Fail closed: LiteLLM's fallback to an empty auth object on failed validation exposed all tools — [Corgea](https://corgea.com/research/cve-2026-59822-litellm-mcp-streamable-http-auth-bypass).
- Model-level defenses are insufficient: Zenity calls soft boundaries (training tweaks, filters, system prompts) "an imaginary boundary" — [CSO Online](https://csoonline.com/article/4036868/black-hat-researchers-demonstrate-zero-click-prompt-injection-attacks-in-popular-ai-agents.html); Invariant says alignment alone is not enough — [Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability); prompt-injection filters cannot grant or restrict DB permissions — [General Analysis](https://generalanalysis.com/blog/supabase-mcp-blog).
- For MCP Apps UI resources: validate `event.origin` and never post with `targetOrigin "*"` — implied by the CVE-2026-76894 fix context — [GitLab advisory](https://advisories.gitlab.com/npm/@aborruso/ckan-mcp-server/CVE-2026-76894/); SEP-1865 mandates sandboxed iframes with auditable communication — [SEP-1865](https://modelcontextprotocol.io/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp).

### Inferences
- A threat→mitigation mapping for the report can be organized as:
  - Malicious authorization_endpoint / OAuth metadata SSRF / mix-up → strict URL scheme allowlist, no shell URL opening, HTTPS enforcement, private-IP blocking, issuer validation, credential-to-AS binding.
  - Confused deputy via OAuth proxy / DCR abuse / consent bypass → per-client consent at MCP layer, exact `redirect_uri` match, CIMD over open DCR, session-bound single-use `state`, `__Host-` cookies, server-side PKCE S256.
  - Token passthrough / audience confusion → audience-restricted tokens (RFC 8707 resource indicators), separate upstream tokens held server-side.
  - Prompt injection → privileged tool call (GitHub, Supabase, AgentFlayer, PromptJacking) → least-privilege scoped credentials, deterministic tool-call policies (Progent/CaMeL), per-session resource confinement, human approval for sensitive actions without "always allow".
  - Rug pull / approval drift → content-hash-bound approval, signed versioned tool definitions (ETDI).
  - DNS rebinding / unauthenticated local proxy / 0.0.0.0 binding → stdio or authenticated loopback, Host/Origin checks on by default, session tokens.
  - Cross-tenant leak → per-request tenant-context authorization, no cross-tenant caching, forced re-auth on remediation.
  - Credential theft at rest / supply chain → secret managers, short-lived delegated tokens, scoped build/hosting tokens, registry provenance checks.
- The recurring meta-lesson is "defaults decide outcomes": most fixes (Inspector session token, SDK DNS-rebinding defaults, Padilla's OAuth-by-default proposal, PaaS-enforced auth at 95%) changed defaults rather than relying on operator configuration.

### Gaps
- NSA CSI's specific authentication/token-lifecycle recommendations not verified (PDF returned 403).
- No empirical study measuring whether these mitigations (e.g., CIMD, per-client consent) reduced incidents after the 2025-11-25 spec update.
- Little published guidance specific to credential handling inside MCP Apps (UI resources calling tools on the user's behalf); only the general SEP-1865 sandbox mandate and one low-severity CVE were found.
