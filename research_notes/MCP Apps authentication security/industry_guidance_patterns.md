# Industry Implementation Guidance and Reference Architectures for Securing Remote MCP Server (and MCP Apps) Authentication — state as of October 2026

Scope note: these notes cover deployment architecture and operational practice as described by identity vendors, cloud providers, AI hosts, and security bodies. They do not re-derive RFC or MCP specification text. Source dates are given where the page exposes one. "GA", "preview", "beta", "early access", and "experimental" labels are as stated by the source at the time it was read (17 Oct 2026). Vendor bias is flagged where a source sells the pattern it recommends.

---

## Q1. What architectural patterns are recommended, and by whom?

### Takeaway
Industry guidance converges on eight distinct patterns. The baseline everyone documents is the MCP server as an OAuth 2.1 resource server that validates audience-bound tokens. The variation is in where the authorization server lives (embedded, external IdP, or gateway), how downstream credentials are obtained (token vault or token exchange, never passthrough), and who grants consent (the user interactively, the enterprise IdP via ID-JAG/XAA, or a human approver out of band via CIBA). Static API keys are tolerated only as a beta or legacy option and are explicitly not a user identity.

### Cited Findings

#### Pattern 1: MCP server as its own (embedded) authorization server
- Components: the MCP client, the MCP server/Worker (which is both the authorization server and the resource server), and optionally an upstream IdP used only for login. Cloudflare's docs list "Worker handles authorization and authentication itself" as one of four options. The flow: client gets HTTP 401, generates PKCE verifier and challenge, opens the Worker's `/authorize`, the user logs in and authorizes, the Worker redirects with a code, the client redeems code+verifier, and the Worker returns access and refresh tokens. (Page last updated 27 Jul 2026.) — [Cloudflare Docs: MCP authorization](https://developers.cloudflare.com/agents/model-context-protocol/protocol/authorization/)
- The Cloudflare getting-started example uses a mock authentication flow. You must implement your own authentication handler or use an external service. — [Cloudflare Docs: MCP authorization](https://developers.cloudflare.com/agents/model-context-protocol/protocol/authorization/)
- Reference implementation `workers-oauth-provider`: it stores tokens, codes, and secrets only as hashes. Per-grant `props` (user data, including upstream tokens) are encrypted so that only the token holder can unwrap them. It supports pre-registered clients, CIMD (`clientIdMetadataDocumentEnabled: true`, which requires the `global_fetch_strictly_public` compatibility flag), and DCR (RFC 7591). It also supports PKCE (RFC 7636), resource indicators (RFC 8707) through a `resources` config with `validateToken(resource, token)`, RFC 9207, RFC 9728, RFC 7009 revocation, and RFC 8693 token exchange. Enterprise-Managed Authorization is marked experimental. The library advertises scopes but does not enforce them. Handlers must check `ctx.auth.scope`. The application owns the `/authorize` page: sign-in, consent, and `completeAuthorization()`. The README references MCP auth spec 2026-07-28 and requires Node 24 or later. — [GitHub: cloudflare/workers-oauth-provider](https://github.com/cloudflare/workers-oauth-provider)
- Hybrid variant ("third-party OAuth"): the Worker is the authorization server facing the MCP client and an OAuth client facing GitHub or Google. Flow: the client starts OAuth at the Worker, which redirects the browser to the third-party `/authorize`. The third party calls back to the Worker with a code, the Worker exchanges it for a third-party access token, and then "generates a bound MCP token." The browser goes back to the client with an MCP authorization code, which the client exchanges for an MCP access token. The client only ever receives the MCP token. — [Cloudflare Docs: MCP authorization](https://developers.cloudflare.com/agents/model-context-protocol/protocol/authorization/)
- Risks addressed: no token passthrough, because the client never holds the upstream token. Responsibility moved onto the server operator: consent UI, client registration, token storage, and scope enforcement (see the library's split of responsibilities above). — [GitHub: cloudflare/workers-oauth-provider](https://github.com/cloudflare/workers-oauth-provider)

#### Pattern 2: MCP server as resource server delegating to an external IdP / authorization server
- OpenAI's reference roles: the resource server is your MCP server, which verifies access tokens on every request. The authorization server is your IdP (or a custom implementation), which issues tokens and publishes discovery metadata. The client is ChatGPT/Codex, acting for the user with OAuth 2.1 authorization code + PKCE. "Customer-specific data or write actions should require authentication." — [OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)
- Anthropic: Claude locates your authorization server through Protected Resource Metadata (RFC 9728). "The authorization server it names can be on a different host from your MCP server." Claude uses only the first entry in `authorization_servers`. — [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- Cloudflare's "bring your own OAuth provider" option names Stytch, Auth0, WorkOS, and Descope. Listed capabilities: email/social/SSO/MFA login, scopes mapped to MCP tools, consent pages, and enforcement that agents invoke only permitted tools. Provider notes: Stytch restricts scopes by role and shows a consent page. Auth0 says access tokens are "automatically refreshed during long running interactions." WorkOS exposes tools conditionally by role/permission. Descope uses custom scopes. — [Cloudflare Docs: MCP authorization](https://developers.cloudflare.com/agents/model-context-protocol/protocol/authorization/)
- Microsoft (platform-integrated variant): App Service / Azure Functions built-in authentication ("Easy Auth") implements MCP server authorization. It validates tokens and applies authorization policies before the MCP initialize request. PRM is configured through the `WEBSITE_AUTH_PRM_DEFAULT_WITH_SCOPES` app setting (PRM support is **preview**). With Entra, the default scope is `api://<client-id>/user_impersonation`. Page ms.date 4 Nov 2025. — [Microsoft Learn: Configure MCP server authorization (App Service)](https://learn.microsoft.com/en-us/azure/app-service/configure-authentication-mcp)
- Microsoft caveat: "MCP server authorization defines access to the server, and it doesn't provide granular control to individual MCP tools." Per-tool authorization must be implemented in the server. — [Microsoft Learn: Configure MCP server authorization (App Service)](https://learn.microsoft.com/en-us/azure/app-service/configure-authentication-mcp)
- Google Cloud's managed remote MCP servers follow the MCP authorization spec. Guidance: give the agent its own principal (agent identity) with least-privilege IAM. A caller needs `mcp.tools.call` on the project plus permissions on the underlying resource. IAM allow/deny policies can key on principal, tool properties such as read-only, service/tool name, and the app's OAuth client ID. IAM-protected services do not accept standard API keys. — [Google Cloud: Authenticate to MCP](https://docs.cloud.google.com/mcp/authenticate-mcp); [Google Cloud: Control MCP use with IAM](https://docs.cloud.google.com/mcp/control-mcp-use-iam)

#### Pattern 3: Auth proxy / gateway in front of MCP servers
- **Azure API Management (APIM)** (page ms.date 11 Sep 2026). Inbound options: (a) subscription key in `Ocp-Apim-Subscription-Key`; (b) OAuth 2.1 / Entra tokens validated with the `validate-azure-ad-token` policy, including an allowlist of `client-application-ids` and a 401 on failure. Outbound: the credential manager injects OAuth tokens for backend calls (register the app at the IdP, create a credential provider, configure connections, then `get-authorization-context` + `set-header`). Samples cover PRM-based authorization and an "Experimental" APIM + Functions remote MCP sample. — [Microsoft Learn: Secure access to MCP servers in APIM](https://learn.microsoft.com/azure/api-management/secure-mcp-servers)
- The same APIM page also documents forwarding the caller's `Authorization` header to the backend with `set-header` (a passthrough option). This is in tension with Microsoft's App Service guidance that passthrough "create[s] security vulnerabilities" (see Pattern 6). — [Microsoft Learn: Secure access to MCP servers in APIM](https://learn.microsoft.com/azure/api-management/secure-mcp-servers); [Microsoft Learn: Configure MCP server authorization (App Service)](https://learn.microsoft.com/en-us/azure/app-service/configure-authentication-mcp)
- Microsoft's earlier reference ("Claude-ready" secure MCP on APIM, 12 May 2025): the APIM gateway acts as the OAuth entry point in front of an MCP server on Azure Functions with Entra. — [Microsoft Developer Blog: Claude-ready secure MCP with APIM](https://developer.microsoft.com/blog/claude-ready-secure-mcp-apim/)
- **Microsoft MCP Gateway (open source, `microsoft/mcp-gateway`)**: a reverse proxy and management layer for MCP servers on Kubernetes. It separates a data plane (`/adapters/{name}/mcp`, plus a tool-router at `/mcp`) from a control plane (CRUD on adapters/tools). Both planes use bearer tokens + RBAC with Entra app roles (`mcp.admin`, plus configurable required roles such as `mcp.engineer`). Write access is limited to the creator or `mcp.admin`. — [Algolia DocSearch index of microsoft/mcp-gateway](https://docsearch.algolia.com/mcp/docs/repo/microsoft/mcp-gateway) (secondary index of the repo; README not read directly)
- **AWS Bedrock AgentCore Gateway**: the gateway is an MCP resource server that requires a valid identity token before AI clients can access any tools. AWS's tutorial uses Cognito but says any organizational IdP works. — [AWS ML blog (mirror): Secure auth code flow with AgentCore Gateway and MCP clients, 2 Jun 2026](https://aihub.hkuspace.hku.hk/2026/06/02/building-a-secure-auth-code-flow-setup-using-agentcore-gateway-with-mcp-clients/)
- AgentCore outbound authorization options: none (not recommended), the gateway IAM service role (SigV4), the caller's IAM credentials (via FAS), OAuth client credentials (2LO), OAuth authorization code (3LO), OAuth token exchange (on-behalf-of), token passthrough (requires inbound `AUTHENTICATE_ONLY`), and API key. Support matrix for **MCP server** targets: none, service role, OAuth client credentials, OAuth auth code, OAuth token exchange, and API key are supported. Caller IAM credentials and **token passthrough are not supported**. Passthrough exists only for AgentCore Runtime (HTTP) targets. — [AWS Docs: AgentCore Gateway outbound auth](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-outbound-auth.html)
- Conflict: a May 2026 third-party tutorial reported that MCP server targets supported only `client_credentials` outbound. The current AWS support matrix lists auth code and token exchange as supported for MCP server targets. — [Security Boulevard tutorial (May 2026)](https://securityboulevard.com/2026/05/connect-aws-bedrock-agentcore-to-an-oauth-protected-mcp-server-a-step-by-step-tutorial/); contradicted by [AWS Docs: AgentCore Gateway outbound auth](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-outbound-auth.html)
- AWS gateway trust-boundary guidance: the gateway execution role is shared across all `GATEWAY_IAM_ROLE` targets and "is the upper bound for what any authorized caller can exercise." Scope it minimally, "use separate gateways for different trust boundaries," and use the policy engine to restrict which callers can invoke which targets. — [AWS Docs: AgentCore Gateway outbound auth](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-outbound-auth.html)
- AgentCore can reach IdPs hosted in a VPC through a private endpoint for OIDC discovery and JWKS. A Runtime accepts exactly one inbound mode, IAM or JWT. — [AWS Docs: AgentCore Identity private IdP](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-private-idp.md)
- **Kong AI MCP OAuth2 plugin** (Kong 3.12+): inbound OAuth 2.0 for MCP traffic, with token verification by introspection or JWKS and claim-to-consumer mapping (`config.consumer_claim`). It is available only in AI Gateway Enterprise and is labeled **tech preview**. No upstream token brokering is documented. — [Kong Docs: AI MCP OAuth2 plugin](https://developer.konghq.com/plugins/ai-mcp-oauth2/)
- **Pomerium** (July 2026 changelog): the MCP gateway discovers upstream OAuth metadata (RFC 9728), completes upstream authorization flows, caches client/token state, and injects upstream access tokens. It uses two tokens: an external token held by the client, and an internal upstream token that Pomerium holds and "is never exposed to external clients." It refreshes upstream tokens before forcing reauthentication. MCP support is labeled **experimental** in some doc versions. — [Pomerium changelog: MCP upstream OAuth, DCR & route discovery](https://www.pomerium.com/changelog/mcp-upstream-oauth-dynamic-client-registration-route-discovery); [Pomerium MCP reference](https://www.pomerium.com/docs/capabilities/mcp/reference); [Pomerium MCP docs (main)](https://main.docs.pomerium.com/docs/capabilities/mcp)
- **Docker**: the Docker Sandboxes MCP gateway gives the sandboxed agent one MCP endpoint. Host-side `sbx` manages registered servers and OAuth credentials (e.g. `sbx mcp auth status notion`), so the credentials stay outside the sandbox. It is distinct from the Docker Desktop MCP Toolkit. — [Docker Docs: Sandboxes MCP gateway](https://docs.docker.com/ai/sandboxes/mcp-gateway/)
- **Google Cloud**: Google recommends routing client traffic to remote MCP servers through a central proxy (on Cloud Run, Apigee, or GKE) that enforces access control, audit logging, secret policies, and secure transport without modifying each MCP server (reported Oct 2025). Google's guidance also covers toolsets as virtual MCP servers that limit tool exposure, and Model Armor to sanitize tool calls and responses. — [InfoQ: Google Cloud secure MCP (Oct 2025)](https://infoq.com/news/2025/10/google-cloud-secure-mcp); [Google Cloud: Control MCP use with IAM](https://docs.cloud.google.com/mcp/control-mcp-use-iam)
- **Cloudflare Access as OAuth provider**: users sign in through a configured IdP or one-time PIN and are admitted only if they match Access policies. The page does not detail token mechanics for this option. — [Cloudflare Docs: MCP authorization](https://developers.cloudflare.com/agents/model-context-protocol/protocol/authorization/)

#### Pattern 4: MCP server (or gateway) as OAuth client to downstream APIs, with a token vault (no passthrough)
- MCP security best practices define token passthrough as an anti-pattern: a server accepts client tokens without validating they were issued to it and forwards them downstream. The upstream token must be a separate token issued by the upstream authorization server. — [MCP Security Best Practices](https://modelcontextprotocol.io/specification/latest/basic/security_best_practices)
- **Auth0 Token Vault** (Auth0 for AI Agents announced **GA** on 19 Nov 2025 by Gareth Davies, CPO): a centralized layer that stores, manages, and refreshes OAuth tokens for third-party systems such as Google Drive, Jira, and Slack. Credentials stay out of agent logic, and admins control which agents reach which systems. The user consents once and later calls reuse the stored token. 35+ listed integrations plus any standard OAuth service. SDK helpers include `with_token_vault` and `get_access_token_from_token_vault`. The post says hard-coded keys are suitable only for dev/test. — [Auth0 blog: Auth0 for AI Agents GA](https://auth0.com/blog/auth0-for-ai-agents-generally-available/)
- **AgentCore Identity token vault**: credentials are accessible only to the specific agent+user combination that obtained them and are encrypted with KMS keys (customer-managed optional). 3LO consent runs through a hosted consent portal attached to a gateway with JWT inbound auth. The gateway service role needs `GetWorkloadAccessToken`, `GetResourceOauth2Token` (on the token-vault credential provider ARN), and `secretsmanager:GetSecretValue`. — [AWS ML blog: Introducing AgentCore Identity (Aug 2025)](https://aws.amazon.com/blogs/machine-learning/introducing-amazon-bedrock-agentcore-identity-securing-agentic-ai-at-scale); [AWS Docs: AgentCore Identity terminology](https://docs.aws.amazon.com/id_id/bedrock-agentcore/latest/devguide/identity-terminology.html); [AWS Docs: AgentCore Gateway outbound auth](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-outbound-auth.html)
- **APIM credential manager** plays the same vault role at the gateway layer: it stores per-connection OAuth tokens and injects them with `get-authorization-context`. — [Microsoft Learn: Secure access to MCP servers in APIM](https://learn.microsoft.com/azure/api-management/secure-mcp-servers)
- **Pomerium** holds internal upstream tokens that are never exposed to clients. — [Pomerium MCP reference](https://www.pomerium.com/docs/capabilities/mcp/reference)
- **Arcade.dev + URL-mode elicitation**: Arcade argued that MCP had no protocol path for a server to obtain third-party credentials. Its SEP, developed with Anthropic, adds URL-mode elicitation: the server sends a URL, the user completes the third-party OAuth in a browser out of band, and the token is never exposed to the client or the LLM. Announced 25 Nov 2025. Vendor bias: Arcade sells this pattern. — [Arcade blog: MCP server authorization guide](https://blog.arcade.dev/mcp-server-authorization-guide); [SiliconANGLE, 25 Nov 2025](https://siliconangle.com/2025/11/25/arcade-dev-anthropic-advance-mcp-new-secure-authorization-flow/); [Arcade, MCP Dev Summit 2026 deck](https://hosted-files.sched.co/mcpdevsummitna26/d1/URL%20Elicitation%20-%20MCP%20Dev%20Summit%202026.pdf)

#### Pattern 5: Enterprise-managed authorization / Cross App Access (ID-JAG)
- Flow (WorkOS, Maria Paktiti, 8 Sep 2026): (1) the user signs in to the MCP client via the enterprise IdP (OIDC or SAML). This is the only browser step, and MFA/conditional access apply. (2) The client sends an RFC 8693 token exchange to the IdP. The IdP evaluates admin policy and returns an ID-JAG (`typ: oauth-id-jag+jwt`, `aud` = the MCP authorization server, with `resource` and scopes). It is returned with `token_type: "N_A"` so it cannot be used as a bearer token. (3) The client redeems the ID-JAG at the MCP authorization server as an RFC 7523 JWT bearer assertion and gets an access token audience-restricted to the MCP server. (4) The client calls the MCP server. Trust prerequisite: the client and MCP server must each already have an SSO relationship with the same IdP. — [WorkOS blog: Inside the ID-JAG](https://workos.com/blog/mcp-enterprise-managed-authorization-id-jag)
- Status: the MCP Enterprise-Managed Authorization extension reached **Stable in June 2026**. The ID-JAG draft is at -04 (21 May 2026), still an IETF WG draft. Okta shipped it as Cross App Access (XAA) and was the first IdP. Clients: Claude, Claude Code, Cowork, VS Code. Servers per the launch: Asana, Atlassian, Canva, Figma, Granola, Linear, Supabase. WorkOS AuthKit's XAA is in early access. Vendor bias: WorkOS sells AuthKit ID-JAG support. — [WorkOS blog: Inside the ID-JAG](https://workos.com/blog/mcp-enterprise-managed-authorization-id-jag)
- Anthropic's implementation ("Enterprise Managed Auth", Claude Team/Enterprise): Claude POSTs `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer` with the assertion, `client_id`, `scope`, and `resource` (when the IdP can forward it) to your token endpoint. There is no browser redirect and no per-connector consent page. Your AS must advertise the jwt-bearer grant in `grant_types_supported` and keep a per-tenant allowlist of trusted issuer URLs. It must reject non-allowlisted `iss` with `invalid_grant` even if the signature is valid, and verify signature, `iss`, `aud`, `exp`, `sub`, and `client_id`. **DCR is not supported with EMA**: the IdP stamps a fixed `client_id` into each assertion, so Claude must be registered via Anthropic-held credentials or CIMD. — [Claude Docs: Enterprise Managed Auth](https://claude.com/docs/connectors/building/enterprise-managed-auth)
- Okta status: Okta announced **GA of "Agent SSO"**, which brings XAA into core Okta SSO plans. "Okta for AI Agents" has been GA since May 2026. Okta expanded the XAA ecosystem on 23 Jun 2026 (25+ launch partners, including Slack, Zoom, Archestra, and MintMCP). The Claude + Okta integration is described as a beta program, and Anthropic links an Okta "XAA beta participation guide." — [Okta press release: Agent SSO](https://okta.com/newsroom/press-releases/okta-brings-first-class-identity-to-ai-agents-with-agent-sso/); [SiliconANGLE, 23 Jun 2026](https://siliconangle.com/2026/06/23/okta-expands-cross-app-access-ecosystem-secure-ai-agent-connections/); [Okta press release: featured IdP for Claude](https://www.okta.com/en-in/newsroom/press-releases/okta-becomes-a-featured-identity-provider-powering-secure-ai-agent-connections-for-claude-enterprise/); [Claude Docs: Enterprise Managed Auth](https://claude.com/docs/connectors/building/enterprise-managed-auth)
- Auth0 (Nov 2025): XAA not yet native; "will soon implement this natively," with a beta sign-up. — [Auth0 blog: Auth0 for AI Agents GA](https://auth0.com/blog/auth0-for-ai-agents-generally-available/)
- Cloudflare's `workers-oauth-provider` marks Enterprise-Managed Authorization as experimental. — [GitHub: cloudflare/workers-oauth-provider](https://github.com/cloudflare/workers-oauth-provider)

#### Pattern 6: On-behalf-of / token exchange at each hop
- **Microsoft**: "The token used for MCP server authorization is meant to represent access to your MCP server, and not to a downstream resource. Pass-through scenarios ... create security vulnerabilities ... obtain a new token through the on-behalf-of flow or another mechanism for explicit delegation." — [Microsoft Learn: Configure MCP server authorization (App Service)](https://learn.microsoft.com/en-us/azure/app-service/configure-authentication-mcp)
- Entra OBO setup pattern (community, Microsoft employee blog): register a public front-end app for the MCP client and a confidential back-end app for the MCP server, with a client secret used for OBO. Expose an API scope on the back end and authorize the front-end client ID. The MCP server then calls Graph or other APIs as the signed-in user. — [Pamela Fox blog, Jan 2026](https://blog.pamelafox.org/2026/01/); [Archestra: Entra OBO for MCP](https://archestra.ai/blog/entra-on-behalf-of-flow)
- **AWS AgentCore Gateway token exchange (OBO)**: the gateway exchanges the inbound user's token for a new, scoped token targeting the downstream resource. "The exchanged token carries both the user's identity and the agent's identity, enabling downstream services to enforce fine-grained authorization at every hop without triggering additional consent flows." — [AWS Docs: AgentCore Gateway outbound auth](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-outbound-auth.html)
- **CoSAI**: "perform token exchange at every trust boundary. Never pass through tokens received from upstream callers." Use RFC 8693 to get a token scoped to the specific operation, keep requests traceable across the chain (end user → intermediate MCP servers → tool), and consider SPIFFE/SPIRE workload identity carried through exchanges. — [CoSAI: After RSAC 2026 (Apr 2026)](https://www.coalitionforsecureai.org/after-rsac-2026-the-mcp-security-question-everyone-kept-asking/)
- Auth0 "Auth for MCP" (Early Access as of Nov 2025) planned "Custom Token Exchange" for connecting to internal APIs. — [Auth0 blog: Auth0 for AI Agents GA](https://auth0.com/blog/auth0-for-ai-agents-generally-available/)

#### Pattern 7: API keys / static tokens (discouraged)
- **Anthropic** supports `static_headers` (an org Owner enters an API key/bearer token once) as **beta for a limited set of organizations**. Rules: read it from a header, "never accept it in the URL" (`?token=`/`?apiKey=` end up in logs, proxies, and history), and treat it as "the organization's credential, not a person's." Every member's requests carry the same key, so don't use it to identify the user. Use OAuth if tools must act as the individual. — [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- **OpenAI**: ChatGPT does **not** support client credentials, service accounts, JWT bearer assertions, custom API keys, or customer-provided mTLS certificates for apps/connectors. — [OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)
- **Microsoft APIM** still documents subscription-key auth for MCP and advises managing keys through VS Code workspace settings or secure inputs. — [Microsoft Learn: Secure access to MCP servers in APIM](https://learn.microsoft.com/azure/api-management/secure-mcp-servers)
- **AWS** supports API-key outbound credentials, stored in the AgentCore Identity token vault and Secrets Manager rather than in agent code. — [AWS Docs: AgentCore Gateway outbound auth](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-outbound-auth.html)
- **OWASP MCP01:2025** (Token Mismanagement & Secret Exposure): hard-coded credentials, long-lived tokens, and secrets in model memory or logs expose connected systems. — [OWASP MCP Top 10](https://owasp.org/www-project-mcp-top-10/)
- Stacklok, citing ecosystem data, says that as of early 2026 only 8.5% of MCP servers use OAuth and 91.5% rely on static API keys, shared tokens, or no auth. It argues static keys are hard to rotate, can't be scoped per request, and give no identity signal for audit. Vendor source. — [Stacklok: MCP security checklist](https://stacklok.com/blog/the-mcp-security-checklist-what-to-verify-before-you-ship-an-mcp-server-to-production/)

#### Pattern 8: Human-in-the-loop / CIBA / async authorization for high-risk actions
- **Auth0 Asynchronous Authorization** (part of Auth0 for AI Agents GA, Nov 2025) uses OpenID CIBA. The agent works in the background and contacts the user only for critical actions. The prompt can show rich authorization details, and the agent gets a token only after the user approves. Channels: Guardian push available, with email/SMS "coming soon" at the time of the post. — [Auth0 blog: Auth0 for AI Agents GA](https://auth0.com/blog/auth0-for-ai-agents-generally-available/)
- **OpenAI**: use the host's confirmation prompts for destructive actions, "require human confirmation for irreversible operations," and make sure users understand when they link accounts or grant write access. — [OpenAI Apps SDK: Security & Privacy](https://developers.openai.com/apps-sdk/guides/security-privacy)

### Inferences
- The patterns are composable layers rather than alternatives. A typical enterprise deployment stacks Pattern 2 or 3 at the edge, Pattern 4 or 6 for downstream calls, Pattern 5 for consentless enterprise onboarding, and Pattern 8 for high-risk tools.
- Gateways split into "validate-only" (Kong, APIM inbound, Easy Auth) and "broker" (Pomerium, APIM credential manager, AgentCore Identity, Docker host-side credentials). Only brokers address the downstream-credential problem.
- Pattern 1's attraction (full control, works with any upstream like GitHub) costs the operator a lot: consent UI, registration abuse controls, token storage, and scope enforcement. Even Cloudflare's library leaves scope enforcement and consent to the app.

### Gaps
- Composio's architecture (managed auth/token storage for agent tools) was not researched in this session. Its token-vault behavior is unverified.
- Scalekit and Keycloak MCP-specific architecture guidance was not retrieved. Keycloak appears only as an introspection backend in Kong examples.
- The Microsoft MCP Gateway README and `entra-app-roles.md` were not read directly. Findings come from a search index.
- The Cloudflare Access-as-OAuth token mechanics (what token Access issues and whether it is audience-bound to the MCP server) are not documented on the page read.
- The official AgentCore Identity GA announcement or date was not retrieved in this session.

## Q2. Per pattern: token issuance, validation, audience binding, scope, refresh, revocation, consent, DCR/CIMD handling, and trade-offs

### Takeaway
Host clients (Claude, ChatGPT) now prefer CIMD over DCR and require PKCE S256, PRM discovery via 401, `resource`/audience binding, and refresh-token rotation for public clients. Major IdPs shipped CIMD during 2025–2026, many still as beta or "manual." Validation is overwhelmingly local JWT/JWKS verification, with introspection offered by gateways such as Kong. The main trade-offs are control vs. operational burden (embedded AS), central governance vs. loss of user-visible consent (EMA/XAA), and gateway convenience vs. passthrough temptation.

### Cited Findings

#### Issuance and client registration as required by the two largest hosts
- **Claude**: supports `oauth_dcr`, `oauth_cimd`, `oauth_anthropic_creds` (Anthropic holds a confidential client you create; contact mcp-review@anthropic.com), `custom_connection` (per-customer client entered at connect time), `static_headers` (beta), and `none`. Claude selects CIMD only when AS metadata advertises both `client_id_metadata_document_supported: true` and `none` in `token_endpoint_auth_methods_supported`, because Claude's CIMD client is public. Otherwise it falls back to DCR. "For servers expecting high traffic from the directory, prefer CIMD or `oauth_anthropic_creds` over DCR. DCR causes Claude to register a new client on every fresh connection." — [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- **Claude**: pure machine-to-machine `client_credentials` is not supported. Anthropic-held credentials are "the consent-gated alternative," and users still see your consent screen. Anthropic-held credentials are bound to the issuing AS, so you must notify Anthropic before migrating authorization servers. They can't be combined with per-customer URL patterns. — [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- **Claude** for per-customer URLs (URL pattern): preference order is CIMD, then DCR, then credentials entered at connection time. — [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- **ChatGPT**: CIMD preferred, with client IDs `https://chatgpt.com/oauth/client.json` (when issuer identification is supported) or `https://chatgpt.com/oauth/{callback_id}/client.json`. With DCR, ChatGPT registers once per MCP server connection and reuses it. CIMD token-endpoint auth: `none` or `private_key_jwt` (ChatGPT JWKS at `/oauth/jwks.json` on the metadata origin). The AS must advertise `code_challenge_methods_supported` including `S256`, or it is unsupported. The page reflects ChatGPT's adoption of the CIMD transition in MCP SEP-3149. — [OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)
- **ChatGPT issuer identification (RFC 9207)**: return `iss` in every authorization response, matching the metadata `issuer` and the PRM `authorization_servers` entry exactly. If `iss` is advertised but missing or mismatched, ChatGPT rejects the response. — [OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)
- **ChatGPT client authentication via mTLS**: ChatGPT presents an OpenAI-managed client certificate. Servers can validate that it chains to the OpenAI Connectors mTLS intermediate CA with SAN `mtls.prod.connectors.openai.com`, and should not pin leaf fingerprints. "mTLS authenticates ChatGPT as the client; OAuth still authenticates the user." — [OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)

#### Validation and audience binding
- OpenAI: treat tokens as untrusted. Verify signature via JWKS, `iss`, `exp`/`nbf`, `aud` or `resource`, and required scopes. On failure return 401 with `WWW-Authenticate` pointing to PRM. ChatGPT sends `resource=<MCP URL>` on both authorization and token requests, and the AS should put it in `aud`. — [OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)
- Claude: the PRM `resource` must equal the MCP URL exactly as the user enters it, including path. A 401 is required to start sign-in, and Claude ignores `WWW-Authenticate` on a 200. — [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- Entra-specific audience binding: Entra compares `resource` against the Application ID URI of the MCP server's app registration and issues `aud` = the MCP server if they match. Claude docs warn you must register the MCP server URL as an Application ID URI or token requests fail with `AADSTS9010010`. A verified custom domain is needed (e.g., not `*.azurewebsites.net`). — [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- `workers-oauth-provider` enforces audience by having resource servers accept only tokens for their own resource via `validateToken(resource, token)`. — [GitHub: cloudflare/workers-oauth-provider](https://github.com/cloudflare/workers-oauth-provider)
- Gateways: Kong verifies by introspection or JWKS. APIM uses `validate-azure-ad-token` with a client-app allowlist. — [Kong Docs: AI MCP OAuth2 plugin](https://developer.konghq.com/plugins/ai-mcp-oauth2/); [Microsoft Learn: Secure access to MCP servers in APIM](https://learn.microsoft.com/azure/api-management/secure-mcp-servers)
- EMA: the AS should accept requests with or without `resource` (some IdP configurations cannot forward it) and use it for audience binding when present. — [Claude Docs: Enterprise Managed Auth](https://claude.com/docs/connectors/building/enterprise-managed-auth)

#### Scopes
- Claude requests the scopes in the `scope` parameter of your 401 `WWW-Authenticate`, or else PRM `scopes_supported`. It appends `offline_access` if the AS lists it, to get a refresh token. — [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- OpenAI: declare `securitySchemes` per tool (`noauth`, `oauth2` with scopes). Listing both means anonymous use is possible but linking unlocks more. The server must enforce auth on every call regardless. — [OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)
- Cloudflare: enforce permissions either by handler-level checks (the error is relayed to the user) or by conditional tool registration, where "the LLM never sees tools the user cannot access." — [Cloudflare Docs: MCP authorization](https://developers.cloudflare.com/agents/model-context-protocol/protocol/authorization/)
- OWASP MCP02:2025 (Privilege Escalation via Scope Creep): loosely defined permissions grow over time. — [OWASP MCP Top 10](https://owasp.org/www-project-mcp-top-10/)

#### Refresh and revocation
- Claude refreshes reactively on 401 and proactively up to 5 minutes before expiry. It expects RFC 6749 `invalid_grant` for dead refresh tokens. Rotate refresh tokens for public clients (DCR/CIMD) and return the new refresh token in the same response that invalidates the old. The `/token` endpoint must accept `application/x-www-form-urlencoded`. Timeouts are 10 s for discovery/registration/token and 30 s for refresh. — [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- OpenAI: handle revocation, refresh, and scope changes, and treat missing or stale tokens as unauthenticated. ChatGPT may send a prior ID token as `id_token_hint` on reauthorization (optional to honor). — [OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)
- EMA: ID-JAG example `expires_in: 300`. Authorization servers SHOULD NOT issue refresh tokens for ID-JAG-based grants, and the client re-exchanges instead. — [WorkOS blog: Inside the ID-JAG](https://workos.com/blog/mcp-enterprise-managed-authorization-id-jag)
- EMA (Anthropic): your AS sets the access token lifetime ("a short lifetime, such as one hour, doesn't force users to repeat single sign-on"). Claude holds a long-lived IdP refresh token and silently gets a fresh assertion as needed, so session length is governed by the IdP refresh token. — [Claude Docs: Enterprise Managed Auth](https://claude.com/docs/connectors/building/enterprise-managed-auth)
- Revocation under XAA (secondary): removing a user in Okta blocks new sign-ins immediately, and active sessions end when the short-lived access token expires (within an hour). — [Context7 docs: Enterprise managed auth with Okta](https://context7.com/docs/enterprise/enterprise-managed-auth/okta)
- Pomerium refreshes upstream tokens before forcing reauth. Auth0 Token Vault refreshes stored third-party tokens automatically. — [Pomerium MCP reference](https://www.pomerium.com/docs/capabilities/mcp/reference); [Auth0 blog: Auth0 for AI Agents GA](https://auth0.com/blog/auth0-for-ai-agents-generally-available/)

#### Consent
- Display the redirect URI hostname clearly on the consent screen, with an extra warning when only loopback redirect URIs are registered ("any local process can bind a port and claim to be the client"). — [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- Entra: pre-authorize known client apps where possible. Some MCP clients (e.g., GitHub Copilot in VS Code) don't surface interactive consent, so pre-authorization is required. — [Microsoft Learn: Configure MCP server authorization (App Service)](https://learn.microsoft.com/en-us/azure/app-service/configure-authentication-mcp)
- EMA removes per-user consent screens. The user-level "notice and decline" check moves to admins, and the IdP's visibility ends at token issuance, so the MCP operator still owns usage audit. — [WorkOS blog: Inside the ID-JAG](https://workos.com/blog/mcp-enterprise-managed-authorization-id-jag)

#### CIMD vendor support status (as of Oct 2026)
- CIMD spec: `draft-ietf-oauth-client-id-metadata-document-02` (July 2026), Standards Track intent, still an Internet-Draft. — [IETF Datatracker: CIMD draft-02](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-02)
- **Okta**: CIMD available for OIDC app integrations and AI agents. The admin points an app at a metadata URL, and Okta fetches and validates it. — [Okta Help: About CIMD](https://help.okta.com/oie/en-us/content/topics/apps/apps-cimd-about.htm)
- **Auth0**: "manual CIMD registration" for third-party applications, plus a Management API endpoint and a tenant toggle to advertise support. Known gaps: CIMD/third-party apps do not support Organizations, and rate limits are pending. — [Auth0 Docs: Register applications with CIMD](https://auth0.com/docs/get-started/auth0-overview/create-applications/register-applications-with-cimd)
- **Stytch**: **beta**, behind a Connected Apps dashboard setting. All CIMD clients are Third-Party Public clients, and validation logic may change. — [Stytch Docs: Client types](https://stytch.com/docs/guides/connected-apps/client-types)
- **Clerk**: beta Aug 2026, **GA 17 Sep 2026**, off by default. Admins can restrict to pre-registered clients only. — [Clerk changelog: CIMD GA](https://clerk.com/changelog/2026-09-17-client-id-metadata-documents-ga)
- **Ping (PingOne Advanced Identity Cloud)**: supported, targeted at large client populations such as MCP agents. — [Ping Docs: OAuth2 CIMD](https://docs.pingidentity.com/pingoneaic/am-oauth2/oauth2-cimd.md)
- **ServiceNow**: supported for public clients with PKCE, but admins still register each client. — [ServiceNow Docs: CIMD inbound](https://www.servicenow.com/docs/r/platform-security/authentication/cimd-inbound.html)
- **Cloudflare `workers-oauth-provider`**: supported (draft-00 behavior). — [GitHub: cloudflare/workers-oauth-provider](https://github.com/cloudflare/workers-oauth-provider)
- **Microsoft Entra ID**: does not support DCR. Clients must be pre-configured with a client ID. (CIMD support for Entra was not found.) — [Microsoft Learn: Configure MCP server authorization (App Service)](https://learn.microsoft.com/en-us/azure/app-service/configure-authentication-mcp)
- **Pomerium**: changelog headline includes upstream DCR. — [Pomerium changelog](https://www.pomerium.com/changelog/mcp-upstream-oauth-dynamic-client-registration-route-discovery)

#### Trade-offs called out by sources
- DCR at scale causes client sprawl (a new client per fresh Claude connection). — [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- A shared, non-per-caller DCR rate limit can lock out legitimate first-time clients (Railway anecdote, workaround: a static OAuth client). — [Railway Station thread](https://station.railway.com/questions/remote-mcp-mcp-railway-com-o-auth-dyn-f192e807)
- CIMD shifts risk to SSRF on metadata fetch and does not solve localhost impersonation or unverified domains. Servers typically cache CIMD docs (about 24 h). — [Descope blog: DCR hardening for MCP, 21 Sep 2025](https://www.descope.com/blog/post/dcr-hardening-mcp); [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- EMA cannot be used with DCR, requires a pre-existing SSO trust triangle per customer, and leaves account linking (IdP `sub` to local user, email collisions) to the implementer. — [Claude Docs: Enterprise Managed Auth](https://claude.com/docs/connectors/building/enterprise-managed-auth); [WorkOS blog: Inside the ID-JAG](https://workos.com/blog/mcp-enterprise-managed-authorization-id-jag)
- Gateway shared execution role is the blast-radius upper bound, so split gateways by trust boundary. — [AWS Docs: AgentCore Gateway outbound auth](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-outbound-auth.html)
- URL-mode elicitation keeps tokens out of the client and LLM but adds redirect UX and multiple authorization steps. — [Arcade blog](https://blog.arcade.dev/mcp-server-authorization-guide)

### Inferences
- In practice, a server that wants to work with both Claude and ChatGPT in 2026 needs an AS that supports PKCE S256, RFC 8707 `resource` → `aud`, RFC 9207 `iss` (ChatGPT), CIMD with `none` auth (Claude), refresh-token rotation, and form-encoded token requests. Entra-only deployments need a front AS or gateway because Entra lacks DCR/CIMD and needs Application ID URI alignment.
- JWT local validation dominates. Introspection appears mainly at gateways (Kong) where opaque tokens or immediate revocation matter.

### Gaps
- WorkOS AuthKit, Descope, Scalekit, Keycloak, and Entra CIMD support status could not be confirmed from primary docs in this session.
- No source gave normative access-token lifetimes for the interactive pattern. The only concrete figures are Anthropic's "such as one hour" (EMA) and the ID-JAG example of 300 s.
- Auth0's "Auth for MCP" was Early Access as of Nov 2025. Its Oct 2026 status was not verified.

## Q3. What do security bodies recommend?

### Takeaway
OWASP, CoSAI, CSA, and NIST/NCCoE align on short-lived, scoped, audience-bound tokens; no token passthrough (token exchange at each trust boundary instead); per-request authorization at the tool boundary; immutable or append-only audit trails; and agent identity distinct from human identity. Most outputs are still beta, draft, or concept-stage as of Oct 2026.

### Cited Findings
- **OWASP MCP Top 10** (project lead Vandana Verma Sehgal; Phase 3 "Beta Release and Pilot Testing"). Auth-relevant entries: MCP01:2025 Token Mismanagement & Secret Exposure; MCP02:2025 Privilege Escalation via Scope Creep; MCP07:2025 Insufficient Authentication & Authorization; MCP08:2025 Lack of Audit and Telemetry (recommends immutable audit trails); MCP09:2025 Shadow MCP Servers (often default credentials); MCP10:2025 Context Injection & Over-Sharing. — [OWASP MCP Top 10](https://owasp.org/www-project-mcp-top-10/)
- **OWASP GenAI Security Project, "A Practical Guide for Secure MCP Server Development"** (16 Feb 2026) covers secure architecture, strong authentication/authorization, strict validation, session isolation, and hardened deployment. Its premise: MCP servers act with delegated user permissions, so a single flaw has outsized impact. — [OWASP GenAI: Practical Guide for Secure MCP Server Development](https://genai.owasp.org/resource/a-practical-guide-for-secure-mcp-server-development/)
- **OWASP GenAI cheat sheet for securely using third-party MCP servers** (v1.0, Oct 2025) covers authentication, authorization, client sandboxing, secure discovery, and governance. — [OWASP GenAI: Third-party MCP servers cheat sheet](https://genai.owasp.org/resource/cheatsheet-a-practical-guide-for-securely-using-third-party-mcp-servers-1-0/)
- **CoSAI (OASIS Open Project) "Model Context Protocol (MCP) Security" white paper**: announced 27 Jan 2026 by OASIS. It covers 12 threat categories and nearly 40 threats, with identity under "MCP-T1: Improper Authentication and Identity Management." Recommendations: trace every request across the chain; do not pass through user-provided OAuth tokens; RFC 8693 token exchange at every trust boundary; SPIFFE/SPIRE workload identities carried through exchanges. Its companion Agentic IAM paper says policy must be evaluated "at every hop and at the last mile." Servers that hold tokens without per-request authorization are confused-deputy exposed. — [OASIS press release, 27 Jan 2026](https://www.oasis-open.org/2026/01/27/coalition-for-secure-ai-releases-extensive-taxonomy-for-model-context-protocol-security); [CoSAI: After RSAC 2026](https://www.coalitionforsecureai.org/after-rsac-2026-the-mcp-security-question-everyone-kept-asking/); [CoSAI MCP Security PDF](https://www.coalitionforsecureai.org/wp-content/uploads/2026/03/model-context-protocol-security-1.pdf)
- Date discrepancy: OASIS announced the paper on 27 Jan 2026, but the currently linked PDF sits under a `/2026/03/` upload path, which suggests a March 2026 revision or re-upload. — [OASIS press release](https://www.oasis-open.org/2026/01/27/coalition-for-secure-ai-releases-extensive-taxonomy-for-model-context-protocol-security); [CoSAI MCP Security PDF](https://www.coalitionforsecureai.org/wp-content/uploads/2026/03/model-context-protocol-security-1.pdf)
- **Cloud Security Alliance** white paper "MCP Security: Tool Poisoning and the Confused Deputy Problem" (16 May 2026). Its confused-deputy section covers token passthrough, over-permissioned static credentials, and OAuth proxy misconfigurations. Recommendations: eliminate token passthrough, per-invocation least-privilege token scoping, policy enforcement at the tool-invocation boundary, and append-only audit logging. — [CSA white paper PDF (16 May 2026)](https://labs.cloudsecurityalliance.org/wp-content/uploads/2026/05/CSA_whitepaper_mcp_security_agentic_attack_surface_20260516-csa-styled.pdf) (content from search extract; the HTML landing page returned 404 when fetched)
- **NIST NCCoE** concept paper "Accelerating the Adoption of Software and AI Agent Identity and Authorization" (initial public draft, Feb 2026; authors Booth, Fisher, Galluzzo, Roberts; comments closed 2 Apr 2026). It proposes a practical lab demonstration of applying existing identity and authorization standards to agentic architectures. It asks about identification, authorization, auditing/non-repudiation, and prompt-injection controls for agents. NIST CAISI launched an AI Agent Standards Initiative in Feb 2026. — [NIST news, Feb 2026](https://www.nist.gov/news-events/news/2026/02/new-concept-paper-identity-and-authority-software-agents); [NCCoE concept paper PDF](https://www.nccoe.nist.gov/sites/default/files/2026-02/accelerating-the-adoption-of-software-and-ai-agent-identity-and-authorization-concept-paper.pdf); [NIST CSRC listing](https://csrc.nist.gov/pubs/other/2026/02/05/accelerating-the-adoption-of-software-and-ai-agent/ipd)
- **Microsoft** (cloud provider guidance): no token passthrough; use OBO or explicit delegation; use a unique identity-provider registration per MCP server ("Don't reuse an existing registration"). — [Microsoft Learn: Configure MCP server authorization (App Service)](https://learn.microsoft.com/en-us/azure/app-service/configure-authentication-mcp)
- **Google Cloud**: a dedicated agent principal with least privilege, deny policies on read-write tools for sensitive resources, a central MCP proxy for policy and audit, toolsets to reduce exposure, and Model Armor. Google's Oct 2025 guide prioritizes five risks: unauthorized tool exposure from misconfigured manifests, session hijacking, shadow tools, token theft/data leaks, and weak-auth bypasses. Context-Aware Access can evaluate device/IP/location signals for agent identities. — [Google Cloud: Control MCP use with IAM](https://docs.cloud.google.com/mcp/control-mcp-use-iam); [InfoQ: Google Cloud secure MCP](https://infoq.com/news/2025/10/google-cloud-secure-mcp); [Google Cloud blog: What's new in IAM](https://cloud.google.com/blog/products/identity-security/whats-new-in-iam-security-governance-and-runtime-defense/)
- **Anthropic** baseline for connector developers: implement MCP authorization including PRM, follow the MCP security best practices, and never accept credentials in query strings. — [Claude Docs: Enterprise Managed Auth](https://claude.com/docs/connectors/building/enterprise-managed-auth); [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- **OpenAI** baseline for app developers: OAuth 2.1 auth code; verify scopes on every tool call; 401 for expired/malformed tokens; least-privilege scopes; "assume prompt injection and malicious inputs will reach your server"; validate model-provided inputs server-side. — [OpenAI Apps SDK: Security & Privacy](https://developers.openai.com/apps-sdk/guides/security-privacy)

### Inferences
- The security bodies are more prescriptive than the vendors on token exchange (CoSAI says "every trust boundary"). Vendors still ship passthrough options in some gateway products (APIM header forwarding, AgentCore passthrough for Runtime targets), so a report should flag passthrough as a configuration risk inside otherwise-recommended gateway architectures.
- None of these bodies has a final, normative MCP auth standard. OWASP is beta, NCCoE is at concept paper, and CoSAI/CSA are white papers.

Third-party summaries disagree on the number of domains (5 vs 8). — [Bastion analysis](https://bastion.tech/blog/owasp-mcp-server-security-guide-analysis); [FlowHunt checklist](https://www.flowhunt.io/blog/mcp-security-checklist-minimum-bar-deployment/)

## Q4. What do vendors recommend specifically for MCP Apps / ChatGPT apps UI authentication?

### Takeaway
Vendors agree that the widget/View (sandboxed iframe) never performs login and never holds the user's access token. Authentication is the host's job: the host's OAuth client runs the flow and stores the token, the widget calls tools back through the host, and the server triggers the host's account-linking UI with a 401/`mcp/www_authenticate` signal on a protected tool. Per-tool security schemes and "lazy authentication" let anonymous tools work until a protected tool is reached.

### Cited Findings
- OpenAI linking UI trigger: both conditions are required. (1) PRM is published and `securitySchemes` is declared on the tool. (2) A runtime tool error includes `_meta["mcp/www_authenticate"]` with `error` and `error_description`. Check tokens inside the tool handler and return this error when no valid token is present. — [OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)
- OpenAI per-tool `securitySchemes` (`noauth`, `oauth2` + scopes). Declare it on every tool even if shared, and omitted means the server default. — [OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)
- Note on standardization: a community thread reports `securitySchemes` is an OpenAI proposal not in the core MCP spec and lives under `_meta["securitySchemes"]` in OpenAI's reference. — [OpenAI Community thread](https://community.openai.com/t/are-chatgpt-docs-lying-about-this-mcp-tool-field-existing/1362688)
- OpenAI widget sandbox: widgets run in an isolated iframe under strict CSP (`connectDomains`, `resourceDomains`, `frameDomains`). Privileged browser APIs are blocked. "Avoid embedding secrets or tokens in component props." Embedded third-party pages carry their own CSP and need their own security review. — [OpenAI Apps SDK: Security & Privacy](https://developers.openai.com/apps-sdk/guides/security-privacy)
- OpenAI multi-account: provide an authenticated, read-only profile tool returning a stable opaque `id`, marked `_meta["openai/profile"]: true`. — [OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)
- OpenAI Enterprise workspace domain restrictions require OIDC discovery, `openid`+`email` scopes, and a UserInfo endpoint returning `email` and `email_verified: true`. — [OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)
- Anthropic "lazy authentication": when a protected tool returns 401 with `WWW-Authenticate`, Claude shows an inline **Connect** card and runs OAuth. If the org has EMA configured, Claude silently performs the JWT bearer exchange and retries the tool call with no prompt. EMA doesn't apply to fully authless servers, which never return 401. — [Claude Docs: Enterprise Managed Auth](https://claude.com/docs/connectors/building/enterprise-managed-auth); [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- MCP Apps (third-party SDK docs): the host's MCP client runs OAuth and stores the access token. The MCP App View does not receive or manage it. Don't put credentials in iframe code, tool results, app state, browser storage, query strings, or logs. The View calls server tools through the host. If a View calls a separate API directly, MCP OAuth does not authorize those iframe requests, so that API needs its own web auth and CORS. — [sunpeak: MCP Apps authorization](https://sunpeak.ai/docs/mcp-apps/mcp/authorization)
- Pomerium's MCP App guide: widget assets are served publicly because the host renders them in a sandboxed iframe and cannot forward auth tokens. Tool calls to the MCP server always require a bearer token, and the widget calls back through the host's server-tool method. — [Pomerium: Develop an MCP App](https://www.pomerium.com/docs/capabilities/mcp/develop-mcp-app)
- Write actions in apps: use host confirmation prompts for destructive actions and require human confirmation for irreversible operations. — [OpenAI Apps SDK: Security & Privacy](https://developers.openai.com/apps-sdk/guides/security-privacy)

### Inferences
- A reference architecture for MCP Apps auth has the host as the only OAuth client and token holder. The widget is an unauthenticated presentation layer whose privileged actions are mediated tool calls, so the server's resource-server checks apply equally to model-initiated and widget-initiated calls.
- Because widget assets may be served publicly, never put user data or secrets in the `ui://` resource itself. Deliver data through authenticated tool results only.

### Gaps
- The official MCP Apps extension specification (ext-apps / SEP-1865) normative text on authentication was not retrieved in this session. Findings rely on OpenAI, Anthropic, and third-party SDK docs.
- Anthropic-specific MCP Apps widget guidance (CSP, token handling in Claude-rendered UI) was not located in the connector auth pages read.

## Q5. Practical checklists: token lifetimes, scope design, logging/audit, DCR abuse protection, redirect URI allowlists, multi-tenant isolation

### Takeaway
Concrete operational controls are available from hosts and vendors. Allowlist the exact host callbacks and loopback patterns; prefer CIMD or pre-registered/Anthropic-held clients over open DCR; harden DCR with tiered rate limits, redirect-domain allowlists, and SSRF-safe metadata fetching; keep access tokens short and rotate refresh tokens; map scopes to tools and enforce them per call; never log raw tokens; keep per-tenant issuer allowlists and per-user permissions.

### Cited Findings

#### Redirect URI allowlists and network trust
- Claude hosted apps (claude.ai web, Desktop, mobile, Cowork): register exactly `https://claude.ai/api/mcp/auth_callback`. Claude Code: loopback on an ephemeral port. Accept `http://localhost/callback` and `http://127.0.0.1/callback` with port ignored (declared in Claude Code's CIMD at `https://claude.ai/oauth/claude-code-client-metadata`). — [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- Customer-entered OAuth clients for Claude must register `https://claude.ai/api/mcp/auth_callback`. — [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- Anthropic egress for allowlisting/conditional access: `160.79.104.0/21`. Discovery requests to your AS come from the same range, so a WAF in front of the IdP can break the flow. — [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- ChatGPT: copy the exact production redirect URI from the app management page. It is either `https://chatgpt.com/connector_platform_oauth_redirect` (stable, when issuer identification requirements are met) or `https://chatgpt.com/connector/oauth/{callback_id}`. Apps published earlier keep the stable URI. — [OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)

#### Protecting DCR from abuse
- Descope (vendor, 21 Sep 2025): use different rate limits for verified and unverified clients; allowlist redirect URI domains; apply IP reputation and geographic restrictions; escalate risk-based flags progressively; give unverified clients the most restrictive session policy; avoid refresh tokens for public clients; audit DCR registrations, consent grants, and tool use into a SIEM; support bulk management and emergency revocation. — [Descope blog: DCR hardening for MCP](https://www.descope.com/blog/post/dcr-hardening-mcp)
- RFC 7591 permits an initial access token to restrict registration to previously authorized parties, and treats rate limiting as optional DoS mitigation rather than a trust control. — [draft-ietf-oauth-dyn-reg-05 mirror](https://potaroo.net/ietf/all-ids/draft-ietf-oauth-dyn-reg-05.html)
- SSRF: DCR metadata URLs (`logo_uri`, `jwks_uri`, `sector_identifier_uri`) are fetched by the AS. PortSwigger research demonstrated SSRF in ForgeRock OpenAM and MITREid Connect. Cloudflare's CIMD support requires the `global_fetch_strictly_public` flag, which restricts fetches to public addresses. — [nhimg.org: Securing DCR on MCP servers](https://nhimg.org/community/agentic-ai-and-nhis/how-to-secure-oauth-dynamic-client-registration-on-mcp-servers); [GitHub: cloudflare/workers-oauth-provider](https://github.com/cloudflare/workers-oauth-provider)
- Prefer CIMD or Anthropic-held credentials for high-traffic servers to avoid client sprawl. — [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- Keep registered clients and secrets valid. Expired or replaced credentials cause `invalid_client`. — [OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)

#### Token lifetimes and handling
- EMA: access tokens of about one hour are fine, because Claude silently re-exchanges. ID-JAG example 300 s, with no refresh tokens for ID-JAG grants. — [Claude Docs: Enterprise Managed Auth](https://claude.com/docs/connectors/building/enterprise-managed-auth); [WorkOS blog: Inside the ID-JAG](https://workos.com/blog/mcp-enterprise-managed-authorization-id-jag)
- Rotate refresh tokens for public clients and return `invalid_grant` on dead refresh tokens. — [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- "Do not log or return the raw access token." — [Cloudflare Docs: MCP authorization](https://developers.cloudflare.com/agents/model-context-protocol/protocol/authorization/)
- Hash tokens at rest and encrypt per-grant upstream secrets (reference design). — [GitHub: cloudflare/workers-oauth-provider](https://github.com/cloudflare/workers-oauth-provider)
- Use a development tenant with short-lived tokens for testing, and debug with MCP Inspector's Auth settings. — [OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)

#### Scope design for agents
- Map scopes to tools. Either hide tools the user lacks permission for (conditional registration) or check in handlers. — [Cloudflare Docs: MCP authorization](https://developers.cloudflare.com/agents/model-context-protocol/protocol/authorization/)
- Request only needed scopes. Verify scopes on every tool call. — [OpenAI Apps SDK: Security & Privacy](https://developers.openai.com/apps-sdk/guides/security-privacy)
- Google: separate read-only from read-write tools via IAM tool properties and deny policies, and use toolsets as virtual MCP servers to cut exposure. — [Google Cloud: Control MCP use with IAM](https://docs.cloud.google.com/mcp/control-mcp-use-iam)
- Auth0 FGA for RAG: filter retrieved documents by user permission (view/comment/edit/share, with group inheritance) before returning them to the agent. — [Auth0 blog: Auth0 for AI Agents GA](https://auth0.com/blog/auth0-for-ai-agents-generally-available/)

#### Logging and audit
- Keep audit logs, redact PII, store correlation IDs, avoid storing raw prompts, and alert on repeated errors or failed auth attempts. — [OpenAI Apps SDK: Security & Privacy](https://developers.openai.com/apps-sdk/guides/security-privacy)
- Immutable audit trails (OWASP MCP08). Append-only audit logging (CSA). Chain-of-custody tracing from end user through intermediate servers (CoSAI). — [OWASP MCP Top 10](https://owasp.org/www-project-mcp-top-10/); [CSA white paper PDF](https://labs.cloudsecurityalliance.org/wp-content/uploads/2026/05/CSA_whitepaper_mcp_security_agentic_attack_surface_20260516-csa-styled.pdf); [CoSAI: After RSAC 2026](https://www.coalitionforsecureai.org/after-rsac-2026-the-mcp-security-question-everyone-kept-asking/)
- Under EMA, the IdP sees issuance but not tool calls, so the MCP operator must audit actual usage. — [WorkOS blog: Inside the ID-JAG](https://workos.com/blog/mcp-enterprise-managed-authorization-id-jag)

#### Multi-tenant isolation
- Scope access with per-user permissions in your service rather than a per-tenant OAuth app. For EMA, keep an explicit per-tenant trusted-issuer allowlist set from an admin control in your product. — [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication); [Claude Docs: Enterprise Managed Auth](https://claude.com/docs/connectors/building/enterprise-managed-auth)
- Per-customer server URLs: Claude validates user-entered URLs against an anchored regex and lowercases the host. — [Claude Docs: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)
- AgentCore token vault binds credentials to the agent+user pair. Use separate gateways per trust boundary. — [AWS ML blog: Introducing AgentCore Identity](https://aws.amazon.com/blogs/machine-learning/introducing-amazon-bedrock-agentcore-identity-securing-agentic-ai-at-scale); [AWS Docs: AgentCore Gateway outbound auth](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-outbound-auth.html)
- Auth0 limitation: CIMD/third-party apps do not support Organizations (Auth0's multi-tenant construct) yet. — [Auth0 Docs: Register applications with CIMD](https://auth0.com/docs/get-started/auth0-overview/create-applications/register-applications-with-cimd)
- OWASP MCP10 (Context Injection & Over-Sharing): shared or persistent context can leak one user's data to another. — [OWASP MCP Top 10](https://owasp.org/www-project-mcp-top-10/)
- Use a unique IdP registration per MCP server. Don't reuse another component's registration. — [Microsoft Learn: Configure MCP server authorization (App Service)](https://learn.microsoft.com/en-us/azure/app-service/configure-authentication-mcp)

### Inferences
- A defensible default checklist for an internet-facing MCP server in late 2026:
  - PRM via 401 and exact `resource`.
  - An AS with PKCE S256, RFC 8707 audience binding, RFC 9207 `iss`, and CIMD (`none`) plus optional hardened DCR.
  - Exact allowlists for the Claude/ChatGPT callbacks and port-agnostic loopback.
  - Access tokens around 1 h with rotating refresh tokens.
  - Per-tool scope checks on every call.
  - A token vault or token exchange for downstream APIs.
  - Human confirmation or CIBA for irreversible actions.
  - Append-only audit with correlation IDs and no raw tokens in logs.
- Rate limiting DCR should be per caller rather than global, so that a flood doesn't lock out legitimate first-time clients (inferred from the Railway anecdote plus the Descope guidance).

### Gaps
- No primary source gave a normative refresh-token maximum lifetime or idle timeout for MCP connectors.
- No source in this session gave a vendor-neutral, quantified DCR rate-limit threshold.
- A third-party summary of OWASP MCP01 mitigations suggested 1–2 hour JWT/OAuth lifetimes and mTLS. That figure couldn't be traced to a specific primary OWASP text, so it is excluded from the findings.
